# 01 — 架构设计文档

本文档描述 kvdb（纯 C 实现的 LevelDB 兼容存储引擎）的整体架构、
关键设计决策以及与 C++ 原版的映射关系。

## 1. 总体结构

```
┌─────────────────────────────────────────────────────────┐
│                 应用程序 (leveldb/c.h)                    │
├─────────────────────────────────────────────────────────┤

│  table_cache.c — 打开的 SSTable 的 LRU 缓存 + BuildTable   │
```

官方 C++ 实现核对行为。

## 2. C 语言下的核心设计决策

### 2.1 错误模型：值语义 Status
C++ 版用 `Status` 对象封装 code+message。C 版设计为**值语义**结构：

```c
typedef struct ldb_status { int code; char* msg; } ldb_status;
```

- 构造函数返回结构体值（成功路径零开销：`{LDB_OK, NULL}`）。
- `msg` 为 malloc 字符串，由 `ldb_status_destroy` 释放。
- 赋值一律走 `ldb_status_set(&s, v)`（先销毁旧值再覆盖），避免泄漏。
- 对外（c_api）按 leveldb 协议转换成 `char** errptr`（malloc 字符串，
  失败时先释放旧值）。

教训：测试宏曾按"接管所有权"设计导致双重释放，最终改为
`CHECK_STATUS_OK/ERR` 内部拷贝一份再报告，调用者保留所有权。

### 2.2 Slice/Buffer 双类型
- `ldb_slice { data, size }`：只读视图，零拷贝传递（对应 leveldb Slice）。
- `ldb_buffer { data, size, cap }`：可增长字符串（对应 std::string）。

两者首两字段布局兼容但类型不同，混用是最主要的错误来源（详见
`doc/04` §B 类错误）。为此提供 `ldb_bslice(&buf)` 辅助函数做显式转换。

**关键语义约束**：`ldb_buffer_remove_prefix` 实现为 memmove（向量语义），
而 leveldb 的 `Slice::remove_prefix` 只推进指针。日志读取器依赖后者
的指针稳定性，因此重写为**显式 pos 游标**而非前缀删除（见 `doc/04` #2）。

### 2.3 面向对象：vtable 结构体
C++ 虚函数用显式方法表模拟，例如迭代器：

```c
typedef struct ldb_iterator_methods {
  void (*destroy)(ldb_iterator*);
  int  (*valid)(const ldb_iterator*);
  void (*seek_to_first)(ldb_iterator*);  ...
} ldb_iterator_methods;

struct ldb_iterator {
  const ldb_iterator_methods* m;   // vtable
  void* impl;                      // 实现指针
  ldb_cleanup_node* cleanups;      // 清理回调链（对应 RegisterCleanup）
};
```

同样的模式用于 Env、SeqFile/RandFile/WritableFile、Cache、Comparator、
FilterPolicy。内部比较器（InternalKeyComparator）通过
`ldb_internal_comparator_adapter` 包装成通用 `ldb_comparator`，
使表层代码可以统一走 `options->comparator`。

### 2.4 所有权与引用计数
| 对象 | 存活策略 |
|---|---|
| MemTable | 引用计数（写路径持 1、DBIter 清理回调持 1、imm 压缩持 1） |
| Version | 引用计数 + 双向链表（dummy_versions 哨兵）；FileMetaData 引用计数 |
| 迭代器持有的状态 | `RegisterCleanup` 链表，destroy 时逆序执行（对应 leveldb 的 CleanupIteratorState） |
| Cache 条目 | 双引用（cache + 外部句柄），refs==1 且在缓存时进入 LRU 链 |
| Compaction | 持 input_version 引用，销毁时释放 |

### 2.5 线程模型
- 一把全局 `impl->mutex`（Windows CRITICAL_SECTION，天然递归；
  POSIX 用 `PTHREAD_MUTEX_RECURSIVE`——递归是必需的，因为 memenv
  的 Schedule 内联执行后台任务，会在持锁状态下重入加锁）。
- `has_imm_`/`shutting_down_` 用原子变量（leveldb 同名语义）。
- 后台压缩通过 `Env::Schedule` 提交；Windows 默认 Env 用单工作线程 +
  FIFO 队列，memenv 内联执行（单调度保证一次只有一个后台任务）。
- 写者队列：`ldb_writer` 链表 + 每写者一个 CondVar，完整复刻
  leveldb 的排队/组提交/唤醒协议。

### 2.6 arena 分配器
memtable 的键值统一在 `ldb_arena` 中分配（4KB 块；超过 1/4 块大小的
分配独立 malloc）。**arena 的内存从不移动**——这是 skiplist 节点键指针
安全的前提。测试中绕过 arena 用可 realloc 的 buffer 存键导致节点键
悬空（见 `doc/04` #T-1）。

## 3. 关键数据流

### 3.1 写路径（`ldb_db_impl_write`）
```
排队(writers_) → 轮到队头 → MakeRoomForWrite:
    bg_error? 阻塞
    L0>=8 文件 → sleep 1ms 降速
    memtable 满(>write_buffer_size) → 切换新 memtable/新 log，
        旧表转 imm → Schedule 后台压缩
    imm 未压缩完 → 等条件变量
    L0>=12 文件 → 等条件变量
→ BuildBatchGroup（≤1MB；leader ≤128KB 时最多 128KB+leader）
→ SetSequence(last+1) → 写 WAL → (sync? fsync) → InsertInto(memtable)
→ last_sequence += count → 唤醒后续写者
```

### 3.2 读路径（`ldb_db_impl_get`）
```
snapshot = 选项快照或 last_sequence
LookupKey(user, snapshot)
memtable.Get → 命中返回
imm.Get    → 命中返回
Version::Get:
    L0: 按文件号新→旧逐个查（bloom → index → data block）
    L≥1: 二分 largest 定位唯一候选文件
    TableCache::Get（LRU 打开 SSTable；block cache 缓存解压后的块）
→ UpdateStats（allowed_seeks--；归零触发 seek 压缩）
```

### 3.3 压缩（BackgroundCompaction）
```
imm 存在 → CompactMemTable（写 L0/L2 表 + LogAndApply）
否则 PickCompaction:
    size 触发(score>=1): 从 compact_pointer_[level] 环形选取
    seek 触发: file_to_compact
    L0: 扩展为所有 key range 重叠文件（+边界文件）
    SetupOtherInputs: 收集 L+1 重叠 → 尝试扩大 L 输入
        （≤25×max_file_size）→ grandparents(L+2)
IsTrivialMove（1 输入 0 父输入 + gp≤10×max）→ 直接改版本
否则 DoCompactionWork:
    合并迭代器逐项 → 丢弃规则 (A) 旧版本被同 key 更新版本遮蔽、
    (B) tombstone 且是 base level → ShouldStopBefore(gp 重叠) 换文件
    → 文件满 2MB 换文件 → InstallCompactionResults → LogAndApply
```

### 3.4 恢复（`ldb_db_open` → `db_recover`）
```
CreateDir + LOCK 独占
CURRENT 不存在? create_if_missing→NewDB : 报错
VersionSet::Recover: 读 CURRENT → 逐条解析 MANIFEST（Builder 合并）
扫描目录: 缺少的表文件 → Corruption
按序重放 log_number 之后的全部 .log（WriteLevel0Table）
last_sequence = max(记录的最大 seq)
LogAndApply 保存新版本 → RemoveObsoleteFiles
```

## 5. 头文件组织

内部只有单一总头文件 `src/kvdb.h`（约 1300 行），包含全部类型与
原型。原因：C 的类型间相互引用多（Version↔VersionSet↔FileMeta 等），
单头文件避免循环包含；代价是改动任一结构体触发全量重编译（本项目
规模下全量编译 < 10 秒，可接受）。

公共 API 单独放在 `include/leveldb/c.h`（与官方逐签名一致），
c_api.c 是唯一同时包含两者的翻译单元。
