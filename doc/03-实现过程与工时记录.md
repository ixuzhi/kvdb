# 03 — 实现过程与工时记录

本文档按时间线记录整个实现过程：每个阶段做了什么、花费的时间、
估算的 token 消耗与难度评级。

**数据说明（重要）**
- **时间**：依据产物文件的时间戳与会话日志重建，为近似值（±10 分钟/阶段）。
- **token**：本会话未开放精确计量。表中数字是**估算值**，方法为：
  `输出 ≈ 写入/改写行数 × 12 token/行`；`输入 ≈ 读取的参考源码行数
  × 10 token/行 + 工具输出（编译/测试日志、目录列表）× 350 token/次`。
  因此表中的 token 应理解为量级参考，而非精确会计。
- **难度**：★1（机械）～★5（需要深刻理解 leveldb 内部不变量）。

## 阶段明细

### 阶段 0 — 环境侦察与工具链（19:16–19:55，≈40 分钟）
- 发现 `leveldb/` 官方源码克隆已在工作目录 → 确定以它为格式权威与
  测试用例来源（无需网络）。
- 系统**没有任何 C 编译器**（无 gcc/cl/llvm/wsl 发行版）；GitHub 直连
  被墙、tuna 目录列表不可用 → 探测到 ghfast.top 代理可用。
- 下载 w64devkit 2.9.1 自解压包（58.6MB），运行解压得到 GCC 16.2。
- **token ≈ 15k（输入为主）；难度 ★2**（纯环境问题，靠代理与
  7z 内嵌偏移两处绕障）。

### 阶段 1 — 参考源码精读（19:55–20:40，≈45 分钟）
- 全文精读：`db_iter.cc`（319 行，解决反向迭代语义疑问——回退扫描
  按"最旧→最新"覆盖直到遇到更小 key）、`db_impl.cc`（1580 行，写路径
  /恢复/压缩全流程）、`version_set.cc`（1570 行，挑选/LogAndApply/
  Builder/AddBoundaryInputs）。
- 精读：`c.h`、`filename.cc`、`table_builder.cc`、`format.cc`、
  `block_builder.cc`、`block.cc`、`table.cc`、`two_level_iterator.cc`、
  `cache.cc`（LRU 引用协议）。
- grep 提取全部关键常量（bloom 种子 0xbc9f1d34、index restart_interval=1、
  kMaxFileSizeForLevel=max_file_size 等——**多个常量与直觉相反**，
  例如输出文件大小并不随层级放大）。
- **token ≈ 60k（输入为主，精读原文占大头）；难度 ★4**
  （需要从 C++ 语义中提炼可移植的不变量）。

### 阶段 2 — 骨架：c.h 复制 / port / kvdb.h（20:40–21:10，≈30 分钟）
- 官方 `c.h` 用 sed 转换（去 export 宏）得到接口头，保证逐签名一致。
- `port.h/port.c`：互斥/条件变量/原子/线程（Win32 + POSIX）。
- `kvdb.h`：约 1300 行的内部总头——全部结构体与原型的设计定稿
  （本阶段最重要的产物，后续模块都按它实现）。
- **token ≈ 30k；难度 ★4**（类型系统设计：值语义 Status、vtable、
  引用计数边界都在此定盘）。

### 阶段 3 — 工具层与环境层（21:10–21:25，≈15 分钟）
- `util.c`（924 行）：buffer/status/coding/crc32c/hash/comparator/
  bloom/arena/uint64_set。bloom 的 k 计算、双重哈希与 leveldb 对齐。
- `cache.c`：16 分片 LRU，引用协议按 cache.cc 逐行对照
  （Ref/Unref/FinishErase/驱逐循环）。
- `env_win.c`：Win32 文件/锁/日志/后台调度。
- **token ≈ 35k；难度 ★3**。

### 阶段 4 — dbformat / skiplist / memtable / log / write_batch
（21:25–22:05，≈40 分钟）
- 逐文件实现；skiplist 保留 leveldb 的随机高度生成器（MINSTD）。
- log writer 的分片与 crc 语义按 log_format.h 落实。
- **token ≈ 40k；难度 ★3**。
- 此阶段埋下了三个后期才暴露的地雷：长度前缀解码的有界性、
  WriteBatch 计数自增缺失、log reader 的 remove_prefix 语义
  （均见 doc/04）。

### 阶段 5 — SSTable 层（22:05–22:35，≈30 分钟）
- `block.c`（534 行）、`table.c`（567 行）、`filter_block.c`、
  `two_level.c`、`iterator.c`（含合并迭代器）、`snappy.c`。
- 自实现 Snappy：变长前导 + literal/copy1/copy2/copy4 + 哈希表贪心
  匹配 + 后向扩展。
- **token ≈ 45k；难度 ★4**（块迭代器的 Prev 与重启点二分细节多；
  snappy 编码器正确性当时被低估）。

### 阶段 6 — version_edit / version_set / table_cache / repair
（22:35–23:00，≈25 分钟）
- `version_set.c` 最终 1818 行（全项目最大）：Builder 合并、
  Finalize 评分、PickCompaction、SetupOtherInputs、恢复。
- bash heredoc **单次命令体积超限导致两次追加截断**，version_set.c
  尾部损坏，回退后改小块重写（过程损耗 ≈ 10 分钟）。
- **token ≈ 45k；难度 ★5**（不变量最多：非重叠层级、compact_pointer
  环形推进、边界文件、grandparent 会计）。

### 阶段 7 — db.c / db_iter.c / repair.c / c_api.c（23:00–23:30，
≈30 分钟）
- `db.c` 1712 行：写者队列、MakeRoomForWrite、DoCompactionWork、
  恢复、属性、DestroyDB；`db_iter.c` 按精读结论移植；
  `c_api.c` 778 行包装层。
- **token ≈ 50k；难度 ★4**。

### 阶段 8 — 测试套件移植（23:30–00:05，≈35 分钟）
- harness（setjmp 失败跳转 + GCC constructor 注册）、9 个测试文件。
- **过程事故**：三次使用 perl 多行正则做批量修改时正则贪婪匹配失控，
  将 test_util.c（膨胀到 12884 行）、test_skiplist.c（8185 行）、
  test_table.c 整体破坏，全部重写（损耗 ≈ 15 分钟）。
  **教训**：对源码的批量编辑一律用 Edit/单行替换，禁用跨行贪婪正则。
- **token ≈ 45k；难度 ★3**。

### 阶段 9 — 构建、调试、修复循环（00:05–00:40，≈35 分钟）
这是整个项目最密集的阶段。首建即通过编译（得益于总头文件先行），
但运行时缺陷成批暴露，按发现顺序（详见 doc/04）：
1. 快照断言（c_api save_error）→ 崩溃链修复；
2. CRC32C Extend/Value 语义 → MANIFEST 校验失败；
3. 长度前缀解码有界性 → memtable 全面 NotFound + 段错误；
4. WriteBatch 计数不自增 → 全部写入不可见；
5. 块句柄解码未推进 → index 指向 metaindex → 压缩后数据丢失；
6. Snappy copy 长度上限 64 + 后向扩展 pos 基准错误 → 块读取损坏
   （用 20 万次模糊测试定位）；
7. log reader 的 memmove 语义 → 首条记录返回错位内容
   （用缓冲区字节级 d0/d7 跟踪定位）；
8. bloom 桥接结构 interior-pointer free → 崩溃；
9. 快照包装层指针类型错位 → 快照被忽略；
10. 合并迭代器缺方向切换 → DBIter::Prev 断言；
11. NULL Compaction destroy、Windows 锁重入、memenv unlink 等
    环境级问题。
- 每轮修复 → 全量 92 测试回归。**token ≈ 90k（本阶段输入输出都很高：
  大量编译/测试回显 + gdb 回溯 + 调试程序往返）；难度 ★5**。

### 阶段 10 — 收尾与文档（00:40–00:55，≈15 分钟）
- 警告清理、README、遗留问题复查（补 `ldb_snapshot_list_smallest`、
  POSIX 递归锁、`env_posix.c`）。
- **token ≈ 25k；难度 ★2**。

## Token 消耗构成（估算）

| 类别 | 估算 token | 占比 |
|---|---|---|
| 参考源码与文档输入 | ≈ 75k | 20% |
| 工具输出（编译/测试/gdb/ls） | ≈ 120k | 32% |
| 写入的代码与文档（输出） | ≈ 130k | 35% |
| 推理与对话（输出） | ≈ 45k | 12% |
| **合计** | **≈ 370k（±20%）** | 100% |

> 说明：输出侧大头是两遍代码（首次实现 + 修复改写）和三次被正则
> 事故破坏后的测试文件重写；输入侧大头是 leveldb 原文精读与
> 30 余轮"编译错误 + 测试失败日志"的往返。若使用精确计量工具，
> 实际数字可能与估算有出入，但量级与比例关系可信。

## 难度评级汇总

| 模块 | 难度 | 主要挑战 |
|---|---|---|
| version_set.c | ★5 | 层级不变量、压缩挑选、Builder 合并、恢复语义 |
| log.c（reader） | ★5 | 分片重组 + 指针稳定性语义 + 损坏恢复路径 |

| db.c | ★4 | 写者队列协议、MakeRoomForWrite 状态机、清理回调 |
| block.c / table.c | ★4 | 迭代器 Prev、index 缩短键、footer/句柄解码推进 |

| db_iter.c | ★3 | 反向扫描的覆盖语义 |

| 测试移植 | ★3 | 需要理解每个断言背后的不变量 |
