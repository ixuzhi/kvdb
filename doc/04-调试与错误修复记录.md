# 04 — 调试与错误修复记录

本文档记录实现过程与后续复核（E-13 起）中发现并修复的全部缺陷。每条按
统一格式：**现象 → 定位过程 → 根因 → 修复 → 验证**。编号规则：
E = 引擎缺陷，N = 平台/环境缺陷，T = 测试代码缺陷。

诊断手段统计：段错误用 gdb -batch backtrace 定位（4 次）；数据损坏
用十六进制字节转储 + 专用最小复现程序（24 个 /tmp/dbg*.c）；压缩器
缺陷用 20 万次随机模糊测试定位；内存与未定义行为用 clang64 的
ASan/UBSan（E-13、N-6）；**泄漏**用原生 Linux 的 LeakSanitizer
（E-16、E-17、E-18，2026-09-20 第二轮，doc/08 §11）；**C 语言使用**用
gcc 12 的严格告警矩阵（`-Wall -Wextra` + 16 个扩展选项）、`-fanalyzer`
与 UBSan 的 nonnull 判定，配 5 个最小复现程序
（`/tmp/cprobe/probe*.c`）定位 E-19…E-25（2026-09-20 第三轮，doc/08 §12）。

## E-1 CRC32C 的 Extend/Value 语义错误
- **现象**：重新打开数据库报 `Corruption: checksum mismatch`；
  所有含重启（reopen）路径的测试失败。
- **定位**：最小复现程序写入 MANIFEST 单条记录再读回 → 第一条记录
  即 EOF。检查读写两侧 CRC 计算公式。
- **根因**：leveldb 的 crc32c `Extend(crc, x)` 在**入口和出口各做一次
  `^= 0xFFFFFFFF`**，从而保证 `Extend(Value(a), b) == Value(a‖b)`。
  我的实现是教科书式"裸寄存器查表"，Value 与 Extend 的组合不满足
  该恒等式 → 写侧 `Extend(Value(type), payload)` 与读侧
  `Value(type‖payload)` 结果不同。
- **修复**：`ldb_crc32c_extend` 加双重异或；`Value = Extend(0, x)`。
- **验证**：RFC3720 全部测试向量 + Mask/Unmask 往返 + Extend 恒等式
  （test_util.c）。此后 MANIFEST 往返复现程序通过。

## E-2 日志读取器使用 memmove 型 remove_prefix（本项目最深的 bug）
- **现象**：reopen 时 MANIFEST 第一条记录返回的内容整体错位
  （读到第二条记录的头部），报 `VersionEdit: unknown tag 98`。
- **定位**：在 `read_physical_record` 内加 `d0/d7` 字节跟踪：解析时刻
  缓冲区内容完全正确（d7=01 为比较器 tag），返回给调用方的内容
  却是偏移 +42 处的字节 → 说明返回的指针在"解析后"被移动了。
- **根因**：leveldb 的 `Slice::remove_prefix` 只做 `data += n`
  （O(1) 指针推进），读取器捕获的 `header` 指针保持有效；我的
  `ldb_buffer_remove_prefix` 是 **memmove**（向量语义），删除前缀后
  数据整体前移，先前捕获的 `header + 7` 指向了错误位置。
- **修复**：重写 `read_physical_record` 为 **pos 游标**模型（缓冲区
  不再移动，显式维护 `r->pos`），完全消除对前缀删除的依赖。
- **验证**：MANIFEST 双记录解析复现程序逐字节比对；全量回归。

## E-3 长度前缀解码错误地施加 5 字节整体边界
- **现象**：写入任何数据后 Get 一律 NotFound；单独使用 skiplist
  时段错误（比较函数读到垃圾）。
- **定位**：dbg5/dbg11 二分定位：直接构造 entry 再调用解码器，
  发现 `vp - entry == 25`（应为 13）。
- **根因**：leveldb 的 `GetLengthPrefixedSlice(p)` 只对 **varint 本身**
  限制 5 字节，数据体长度不受限（`Slice(p, len)` 可越过 limit）。
  我的 `ldb_get_length_prefixed_slice` 把 limit 当作整体边界 →
  任何 >5 字节的条目解码失败。
- **修复**：新增 `ldb_get_length_prefixed_slice_unbounded`（varint 限
  5 字节、数据体无界），memtable 比较器/迭代器/Get 全部换用。
- **验证**：dbg24 复现程序 + 全量回归。

## E-4 WriteBatch 计数不自增
- **现象**：所有 Put 后 `count==0`，数据写入 memtable 为空，
  Get 一律 NotFound（在 E-3 修复后暴露）。
- **定位**：dbg6 逐层复现：`count=0, bytes=25, seq=0` → put 没有更新
  头部计数字段。
- **根因**：leveldb 的 `WriteBatch::Put/Delete` 第一行是
  `WriteBatchInternal::Count(this)++`，移植时遗漏。
- **修复**：put/delete 前调用 `set_count(count+1)`。
- **验证**：dbg3（引擎级 put/get）+ 全量回归；write_batch 测试断言
  计数与迭代内容。

## E-5 块句柄解码不推进输入
- **现象**：压缩后数据全部丢失（版本为空）；SSTable 迭代器 0 条目；
  footer 解出的 index_handle == metaindex_handle。
- **定位**：在 table open 打印 footer 两个句柄发现二者完全相同 →
  footer 解码连续读出同一 varint 对。
- **根因**：leveldb 的 `BlockHandle::DecodeFrom` 解码后**推进输入
  Slice**（连续解码 metaindex、index 两个句柄）；我的实现读完不推进
  → 第二次解码重复读第一个句柄 → index 指向 metaindex（空块）→
  表迭代器永远无效，压缩输出虽写出但查找全失败。
- **修复**：`ldb_block_handle_decode` 成功后 `input->data += p; size -=`。
- **验证**：dbg17（文件级迭代 91 条 + tc_get 命中）+ 全量回归。

## E-6 Snappy：单条 copy 指令长度超上限
- **现象**：`Corruption: corrupted snappy compressed block contents`；
  大块（重复值多、匹配长）读取失败，小块正常。
- **定位**：dbg18 用表级真实数据复现；写十六进制分块解析器逐 chunk
  检查发现 copy4/copy2 的 len 字段异常。
- **根因**：Snappy 所有 copy 指令的 length-1 只占 6 位（len ≤ 64），
  长匹配必须拆成多条 copy。我的编码器把任意长度塞进一条 copy，
  `(len-1)<<2` 静默截断 → 流损坏。
- **修复**：`emit_copy` 循环拆分（≤11 且偏移 <2048 用 copy1，
  ≤64 用 copy2/copy4，更长则以 64 为步长重复——重叠拷贝语义合法）。
- **验证**：20 万次三模式模糊测试（重复值/全随机/长游程）全部往返
  一致；压缩率与预期一致（重复数据 >12.5% 收益）。

## E-7 Snappy：后向扩展后 pos 基准错误
- **现象**：模糊测试 `MODE 1 trial 160` 解压失败，copy 偏移出现
  30 亿级垃圾值。
- **定位**：模糊测试提供的最小失败用例 + 解析器输出对齐检查。
- **根因**：后向扩展把匹配起点从 `pos` 移到 `new_pos`，但循环末尾
  `pos += len; next_emit = pos;` 仍用旧 pos → `next_emit` 超前于
  实际输出位置 → 后续 literal/copy 的相对偏移全部失真。
- **修复**：`pos = new_pos + len; next_emit = pos;`，哈希插入也改为
  new_pos 基准。
- **验证**：模糊测试全绿（3 模式 × 200 次）。

## E-8 bloom C API 桥接结构释放内部指针
- **现象**：`c_api.BloomFilterOption` 测试进程段错误（发生在关闭与
  filterpolicy_destroy 时）。
- **定位**：gdb 回溯到 `leveldb_filterpolicy_destroy` → `free(&b->api)`。
- **根因**：`bloom_bridge` 结构把 `leveldb_filterpolicy_t api` 作为
  **内嵌成员**，destroy 时 `free(内嵌地址)` 是 interior pointer 释放
  → 堆损坏。
- **修复**：api 独立分配，bridge 只作 state；析构函数先销毁内部
  bloom 策略再释放 bridge。
- **验证**：bloom 测试 + ASan 式多次开关数据库回归。

## E-9 C API 快照指针类型错位
- **现象**：经快照读取仍返回最新值（快照被无视）。
- **定位**：内部 API（dbg12）行为正确 → 问题在 C API 包装层。
- **根因**：`leveldb_readoptions_t.snapshot` 指向包装结构
  `leveldb_snapshot_t { rep; }`，实现里把它**直接当成**
  `ldb_snapshot_impl*` 解引用 → 读到的是 `rep` 指针值本身当作
  sequence（超大值 → 一切可见）。
- **修复**：`to_ldb_read_options` 解包 `snapshot->rep`。
- **验证**：dbg12 内部/外部对照 + c_api.Snapshot 测试。

## E-10 NULL Compaction 的析构
- **现象**：`CompactRange(NULL, NULL)` 段错误。
- **定位**：gdb 回溯 `ldb_compaction_destroy(c=0x0)`。
- **根因**：手动压缩区间内没有文件时 `CompactRange` 返回 NULL，
  C++ 的 `delete nullptr` 合法而 C 的 destroy 未判空。
- **修复**：destroy 入口 `if (c == NULL) return;`。
- **验证**：dbg13 + CompactRange 测试。

## E-11 合并迭代器缺少方向切换
- **现象**：`db.IterPrev` 断言失败（`mg->direction == 1`）后中止。
- **定位**：断言现场即答案：DBIter::Prev 在 forward→reverse 切换时
  对处于 forward 状态的合并迭代器直接调 Prev。
- **根因**：leveldb 的 `MergingIterator::Next/Prev` 在方向不符时执行
  **全体子迭代器重定位协议**（除当前子迭代器外，其余 seek 到当前
  键、Next/Prev 一步），我的初版只处理了"已经在正确方向"的情况。
- **修复**：按 leveldb 精确算法实现双向切换。
- **验证**：db.IterPrev + 多版本快照迭代测试。

## E-12 描述文件记录了错误的比较器名
- **现象**：reopen 报 `Invalid argument: leveldb.InternalKeyComparator
  does not match existing comparator`。
- **根因**：`NewDB` 与 `repair` 写入的是内部比较器名（经 sanitize 后
  的 options.comparator），而 leveldb 记录的是**用户比较器名**。
- **修复**：两处改为 `internal_comparator.user_comparator->name(...)`。
- **验证**：reopen 测试 + RepairOpenDB 测试。

## E-13 SSTable footer 的 padding 落的是堆残留（doc/06 P0-7）
- **现象**：与真实 leveldb 逐字节比对时，同一份内容两边写出的 `.ldb`
  尾部 20 字节不同——官方是 `0x00`，kvdb 里是上一轮留下的 `"golden"`、
  `"key"` 文本。
- **定位**：先固定负载（`tests/interop/golden_driver.c`）保证两边输入
  完全一致，再对差异文件做 first-difference，落点恒在 footer 的
  padding 区（48 字节 footer 先用 `resize` 补到 40 再追加 magic）。
- **根因**：`ldb_buffer_resize` 增长时只保证容量、不清零，而复用的
  buffer 常带着上一块的旧内容；`std::string::resize` 会把新字节写成
  `\0`。C++ 侧"免费的"保证在 C 侧必须自己做。
- **修复**：`src/util.c` 增长路径 `memset` 补零。
- **验证**：`format_extra.FooterPaddingSurvivesDirtyReusedCapacity`。
  负向对照：摘掉补零后，125 例中**只有**这条新例失败——原测试集对这个
  缺陷完全无感。

## E-14 arena 缺 AllocateAligned，跳表节点按未对齐地址强转（doc/06 P0-8）
- **现象**：UBSan 报 `load of misaligned address ... skiplist.c:31`，
  指向 `ldb_skiplist_node` 的 `key`/`next[]` 读取。Windows 与 x86-64
  对非对齐访问宽容，所以 127 例从未失败。
- **定位**：对照 leveldb `db/skiplist.h` 的 `NewNode`：它对节点用
  `Arena::AllocateAligned`，而 kvdb 的 arena 只有裸 bump 版
  `ldb_arena_allocate`。memtable 条目按变长布局交替分配，节点地址
  的奇偶完全由前一个条目决定。
- **根因**：把 `Allocate` 与 `AllocateAligned` 两个 API 缩减成了一个，
  强转 `void*` 的那一侧失去了对齐保证。
- **修复**：`src/util.c` 补 `ldb_arena_allocate_aligned`（8 字节对齐 +
  与 leveldb 相同的 slop 计算，fallback 分支因 malloc 天然对齐不加
  slop），`skiplist.c` 的 `node_new` 改用它。
- **验证**：`arena.AlignedAllocationsSurviveOddSizedNeighbours`（奇数
  大小分配与对齐分配交替，断言 `%8==0` 并真的写入 `key`/`next[]`）；
  摘掉修复后 UBSan 立刻复报。

## E-15 `get_range2` 向 `memcpy` 交 NULL，glibc 的 nonnull 声明把它判成 UB（doc/06 P0-10）
- **现象**：原生 Linux 上 `scripts/run_sanitizers.sh`（gcc 12 +
  `-fsanitize=address,undefined -fno-sanitize-recover=all`）首跑，127 例套件
  与未修改的官方 `db/c_test.c` 同时终止在一条报告：
  `version_set.c:1448: runtime error: null pointer passed as argument 2,
  which is declared to never be null`，栈为
  `get_range2 ← vs_setup_other_inputs ← pick_compaction ← background_compaction`。
  `unit.log` 里 8 次命中全在同一行；c_test 停在 `Test repair` 阶段。
  clang64 腿此前跑的是同一份代码，零报告。
- **定位**：`get_range2` 把两个输入数组用两次 `memcpy` 拼成一个；
  `SetupOtherInputs` 在"该层没有其它文件"时交的是 `NULL + 0`。查 glibc 头文件
  可知 `memcpy` 的形参带 `__attribute__((nonnull))`，UBSan 的
  `nonull-argument` 检查因此报罚；Windows 侧的 libc++/msvcrt 没有这个属性声明，
  所以同一份代码在 clang64 下静默通过——**这是"换 libc 才看得见"的一类**。
- **根因**：向 `memcpy` 交 NULL 即使长度为 0 也是 C 标准意义的 UB，被内联展开的
  `memcpy` 同样可以假定实参非空并据此优化。对照官方
  `version_set.cc::GetRange2`：它用 `std::vector` 拷贝 + `insert` 合并，
  从不交出空基址。故本条属 C 重写引入，不是从 leveldb 继承。
- **修复**：`src/version_set.c` 的两次拷贝各加 `n1 > 0` / `n2 > 0` 守卫；
  `n == 0` 时目标侧 `all`（`malloc(0)` 可能返回 NULL）也一并避开被写。
- **验证**：字节中性——修复后 L1 黄金比对仍 109 项 PASS、33 个文件与官方逐字节
  相同，L0 仍 127/0，L3 全链（127 例 + 官方 c_test 16 阶段 + `golden_driver`
  10 负载 create/verify）零 sanitizer 报告。留档
  `build/san-runs/interop-20260919-051449/`，过程详录 doc/08 §5。

## E-16 `recover_log_file` 读完不销毁 log reader（doc/06 P2-9 的泄漏半边）
- **现象**：2026-09-20 把延后了两轮的 T1（LeakSanitizer 维度）实跑，
  `SAN_DETECT_LEAKS=1 bash scripts/run_sanitizers.sh` → `rc=1`，
  `SUMMARY: AddressSanitizer: 929842 byte(s) leaked in 201 allocation(s)`
  （127 例套件）、`33328 byte(s) / 10 allocation(s)`（官方 c_test）、
  `golden_driver` 每个负载 create 阶段 126–135 B / 2 个分配。
  其中 **917,504 B 是 `Indirect leak`**，栈为
  `ldb_buffer_reserve (util.c:28) ← ldb_buffer_resize ← ldb_log_reader_new
  (log.c:129) ← recover_log_file (db.c:436) ← db_recover ← ldb_db_open`，
  占全部泄漏的 98.7%；另有 2,688 B / 28 个 reader 结构本身是直接泄漏。
- **定位**：`ldb_log_reader_new` 全仓五个调用点（`repair.c:86`、
  `version_set.c:1192`、`test_log.c:44`、`test_recovery_extra.c:69`、
  `db.c:436`），前四个都成对调用 `ldb_log_reader_destroy`，只有
  `recover_log_file` 读完循环后直接往下走。官方
  `db_impl.cc::RecoverLogFile` 的收尾正是 `delete reader; delete file;`。
- **根因**：reader 自带一整块 `LDB_LOG_BLOCK_SIZE`（`kvdb.h:668` = 32,768 字节）
  读缓冲（`log.c:115-137` 的 `new` 分配、`destroy` 归还），所以泄漏量是"每次恢复
  一个 WAL ≈ 32 KB"而不是几十字节；开关库越频繁增长越线性。28 个间接对象 ×
  32,768 = 917,504 B 与该组报告值精确对上。结构体只 96 B 而缓冲 32 KB，
  也解释了"间接远多于直接"这个形状。
- **修复**：`src/db.c` 读循环结束后、`ldb_write_batch_destroy(&batch)` 之前
  补 `ldb_log_reader_destroy(reader);`。
- **验证**：该族 920,192 B 全部归零（917,504 + 2,688 = 修复总量的 99%）。
  负向对照（证明 LSan 这一维度真的在起作用）：把这一行临时换成一次故意的
  `ldb_log_reader_new(NULL, NULL, NULL, 0, 0)`，同一条腿立刻
  `rc=1 / 1,840,384 byte(s) leaked in 112 allocation(s)`，脚本
  `build/san-runs/interop-20260920-002934/`。字节中性：L1 的
  `results.tsv`（145 行逐条判定）与修复前一遍逐字节 `diff` 为空。

## E-17 值语义 `ldb_status` 在"故意忽略错误"处不还 `msg`（doc/06 P2-9）
- **现象**：同一轮 LSan 报出 8,002 B / 91 个 `ldb_status_new (util.c:106)`
  对象，按"第一个非 env 栈帧"聚成三组，其中只有第一组属于引擎：
  **5,760 B / 69 个来自 `ldb_db_impl_new (db.c:63)`**（memenv 46 + posix 23，
  即每次开库 `create_dir`/改名旧 LOG 那几次丢弃）；另两组各 1,121 B / 11 个，
  都在 `ldb_test_destroy_dir (test_main.c:60 与 :69)`，即脚手架的
  `ldb_env_get_children` 与 `ldb_env_delete_dir`（记为 **T-12**，共 2,242 B / 22）。
  **其余 20 多处丢弃一条也没报**——它们只在**错误路径**上才有 `msg` 可泄，
  而这四条腿测到的运行里这些调用全部返回 ok（成功状态不持有堆内存）。
  它们由下面的机械扫描找出、按同一惯用法一并改掉，属预防性修复而非逐条实测所得。
- **定位**：不靠肉眼看栈。把 `src/kvdb.h` 里 48 个返回 `ldb_status` 的函数
  名当作词表，机械扫 `src/`+`tests/` 中"作为表达式语句出现"的调用，得到
  **src 17 处 + tests 脚手架 4 处**语句级丢弃；再扫 `if (ldb_ok(<调用>))`
  这种把状态塞进条件、连变量都没有的形式，又得 **6 处**（`db.c:65`、
  `table.c` 的 375/416/523、`c_api.c:290`、`test_main.c:60`）。扫出的结果
  逐条人工复核：`block.c:514`/`version_set.c:348` 是 `return
  ldb_status_corruption(...)` 的换行续行、`version_set.c:1117` 是跨行赋值，
  三处假阳性剔除；`ldb_version_edit_encode`（`db.c:166`、`repair.c:262`）
  恒返回 `ldb_status_ok()`，没有 `msg` 可泄，不改；`test_table.c:165` 的
  `ldb_table_internal_get` 其实已命名并 `CHECK_STATUS_OK`，只在失败路径上
  少一次销毁（那次运行本来就算 FAIL）。哪些函数的状态真会带堆 `msg`：
  env 系列、`ldb_read_block`、`ldb_block_handle_decode`、
  `ldb_write_batch_insert_into` 都会。
- **根因**：官方 C++ 的 `Status` 是 RAII，`env->RemoveFile(f);` 丢弃返回值
  一分钱不花；kvdb 的 `ldb_status` 是**值类型 + 堆 `msg`**（`kvdb.h:109`），
  丢弃即泄漏。更要紧的是它**只在错误路径上**泄漏——"忽略错误"的代码平时
  走不到那条分支，所以 127 例、官方 c_test、黄金比对在没有 LSan 之前
  一条都不会红。这一族与 E-16 同属"C 重写丢掉了 C++ 的析构习惯"。
- **修复**：`src/kvdb.h` 新增 `ldb_status_release()`，语义就是官方那句
  "不命名地丢弃一个 Status"，21 处语句级丢弃全部显式改走它
  （`db.c` 的 60/63/116/185/225/256/280/1037/1712/1713/1714、`dbformat.c:134`、
  `version_set.c:1136`、`repair.c` 的 98/185/227/276、`test_main.c` 的
  44/49/64/69）；6 处 `if (ldb_ok(<内联调用>))` 改成命名局部 +
  `ldb_status_destroy`；`ldb_destroy_db` 另补两条同源分支——`get_children`
  失败即 `return ldb_status_ok()` 前不销毁 `result`，以及随后
  `result = ldb_env_lock_file(...)` 直接覆盖旧值，现分别改为先
  `ldb_status_destroy` 与改用 `ldb_status_set`。合计 29 处。
- **验证**：`ldb_status_new` 一族归零（LSan 总量 929,842 → 0）；六处
  `if (ldb_ok(...))` 改写为控制流等价（短路顺序保持：`filter == NULL`
  时仍不调用 `ldb_block_handle_decode`）；L0 仍 127/0 且 6 条警告一字
  未变，L1/L2 判定逐行不变。

## E-18 `db_new_db` 不销毁 `ldb_version_edit`
- **现象**：LSan 报 1,568 B / 49 个直接泄漏，栈一律是
  `ldb_buffer_reserve ← ldb_buffer_append ← ldb_buffer_append_str ←
  ldb_version_edit_set_comparator (version_edit.c:72) ← db_new_db (db.c:146)`
  ——黄金驱动每个负载 126–135 B / 2 个分配里的那一个 32/96 字节小件。
- **定位**：`ldb_version_edit_init` 全仓七个调用点，六个成对
  `ldb_version_edit_destroy`（`version_set.c:1016/1045`、`1200/1237`、
  `1332/1343`、`db.c:567/596`、`1631/1661`、`repair.c:247/263`），
  只有 `db_new_db` 一个都没有，且它有两条退出路径（`new_writable_file`
  失败早退与正常返回）。
- **根因**：`ldb_version_edit::comparator` 是 `ldb_buffer`，
  `set_comparator` 把比较器名 append 进堆；官方
  `VersionEdit::SetComparatorName` 存 `std::string`，随对象自动析构。
- **修复**：两条退出路径各补一次 `ldb_version_edit_destroy(&new_db)`。
- **验证**：该族归零；新建库路径的落盘字节不变（L1 的 `results.tsv`
  逐行相同）。

## E-19 internal filter policy 是进程级单例（doc/06 文末"第三轮"小节的 D-1）
- **现象**：不崩、不报错，是被 LSan **反向**暴露的：`ldb_get_internal_filter_policy()`
  返回 `static ldb_internal_filter_policy ifp_singleton` 的地址，全进程只有这一份，
  每次开库都往同一块内存里重写 `user_policy`。
- **定位**：本轮 C 语言使用检查里问"谁持有这个包装器"。官方把它做成两个成员——
  `DBImpl::internal_filter_policy_`（`db/db_impl.h:161`）与
  `Repairer::ipolicy_`（`db/repair.cc:431`，且是 `const`）——生命周期分别随
  DBImpl / Repairer；本仓做成了文件级 `static`。可推的直接后果有两个：后开库会覆盖先用者的
  `user_policy`（两库若用**不同类型**的策略，前者的 filter 就会被后者解释）；
  以及写这块全局发生在 `ldb_db_impl_new` 里、在拿到任何锁之前，两个线程同时开库
  就是纯数据竞争。用 `-fsanitize=address` 的交叉开库探针
  （`/tmp/cprobe/probe3.c`，A=bloom/10、B=bloom/1000）实测**看不出差别**，
  原因是 `bloom_key_may_match` 的 `k` 从 filter 最后一个字节里取、
  `bits_per_key` 根本不参与判定（doc/06 记过这条），两个 bloom 策略互换在行为上
  不可分辨——所以这一条是"设计上必错、当前测试打不到"，不是"实测到的错误读数"。
  真正实测到的后果是它的**副作用**：这块全局把调用方漏销毁的策略永久钉成
  "全局可达"，LSan 因此一条都不报（见 T-14）。
- **根因**：C++ 的"每实例一个成员"在 C 重写时图省事落成了文件级 `static`。
- **修复**：API 改为 `ldb_init_internal_filter_policy(ldb_internal_filter_policy* self,
  const ldb_filterpolicy* user_policy)`，存储由调用方出；`ldb_db_impl` 新增
  `internal_filter_policy` 字段（位置紧跟 `internal_comparator_adapter`、在
  `options` 之前，因为 `options.filter_policy` 存的就是它的地址），
  repairer 新增 `ipolicy`（见 E-20）；头文件把生命周期写进注释。
- **验证**：130 例 + L1/L2/L3 全绿；解除抑制后当场逼出 T-14 那 144 B / 3 个对象。

## E-20 `ldb_repair_db` 没有包装 filter policy（D-2）
- **现象**：修复一个带 bloom 的脏库（WAL 里有 200 个键、未 flush）后重开，
  **200 个点查全部 NotFound**。
- **定位**：`/tmp/cprobe/probe5.c` 在 pristine HEAD 上跑两种配置：带 bloom/10 时
  `missing=200/200`，完全不带策略时 `missing=199/200` → 后者说明另有一个与策略
  无关的缺陷（E-21），前者是两者叠加。再把 D-3 单独打成补丁
  （`/tmp/kvdb-head2` + `probe5-head2`）：无策略侧回到 `0/200`，带策略侧仍
  `199/200` → 剩下的 199 个确实归策略。
- **根因**：repair 建表与读表都走内部键，官方 `Repairer` 因此持有
  `ipolicy_` 并把 `options_.filter_policy` 换成它；本仓只换了 `comparator`
  （`r.options.comparator = &r.adapter`），`filter_policy` 原样留着用户策略
  → 写表时按 **user key** 建 filter，点查时按 **internal key** 问它，几乎必然 miss。
- **修复**：`repairer` 增 `ldb_internal_filter_policy ipolicy;`，在 sanitize 副本之后
  `r.options.filter_policy = ldb_init_internal_filter_policy(&r.ipolicy, options->filter_policy);`。
- **验证**：`probe5-fixed` 两配置均 `missing=0/200`；新增用例
  `db.RepairWalWithBloomFilter`（`tests/test_db.c`）在 HEAD 上 FAIL
  （`FAIL tests/test_db.c:718: check failed: 1 == dbt_get(...) (1 vs 0)`）、
  在本轮代码上 PASS。该用例故意在 repair 之后**删掉 WAL**，让转换出的表成为唯一
  副本——不删的话重开库会重放 WAL，把 E-20 与 E-21 一起盖住（第一轮探针
  就是因为这个"证明不了任何东西"）。

## E-21 WAL 转换出的表绕过了 phase 3（D-3）
- **现象**：不带任何 filter policy 时，修复脏库后 `missing=199/200`；
  修好后 MANIFEST 记录从 80 B 变 81 B。
- **定位**：`convert_log_to_table()` 把新表的 `ldb_file_meta` **复制**进
  `r->tables`（phase 4 用来登记的那份），而 phase 3 遍历的是 phase 1 扫盘得到的
  局部 `tables[]`。脏库里本来没有表，于是 phase 3 一次都没跑：新表既不被
  `scan_table` 校验、也不进 `max_sequence`。`max_sequence` 保持初值 1，
  `last_sequence` 就被写成 1；读路径以 `last_sequence` 为快照上界，WAL 里 200 个
  条目的序列是 1..200，只有 seq=1 的那一个可见 → 恰好 199/200。80→81 B 就是
  `last_sequence` 的 varint 从 1 字节进到 2 字节（200）。
- **根因**：官方明确不这么做。`db/repair.cc:200` 就地写着 "Do not record a version
  edit for this conversion to a Table since `ExtractMetaData()` will also generate
  edits."，`:212` 只是 `table_numbers_.push_back(meta.number)`，让
  `ExtractMetaData()`（本仓的 phase 3）统一扫。本仓把"登记"提前做了，就漏了"扫"。
- **修复**：`convert_log_to_table()` 改为把 `tnumber` 推给调用方的
  `tables[]`（签名多三个参数），phase 3 因此校验它、登记它、把它条目的最大序列
  折进 `max_sequence`；函数内的 `meta` 改为**无条件** `ldb_file_meta_destroy`。
- **验证**：`probe5-head2`（只打 D-3）无策略侧 `0/200`、`probe5-fixed` 两配置
  `0/200`；落盘差异只有那 1 字节，且只在 repair 路径上（repair 不在 L1 黄金比对的
  负载里）。**中途反复**：第一版把 `ldb_file_meta_destroy` 留在 `else` 分支，
  推进列表后 meta 的键缓冲等于被两处持有却只销毁一次，LSan 当场报
  64 B / 4 个对象（`table_cache.c:158/163` 经 `repair.c:124`）；改成无条件销毁后归零，
  注释里写明"phase 3 会自己重新导出 meta，所以这里什么都不保留"。

## E-22 `{NULL, 0}`  slice 进 `memcpy`：E-15 同族补齐四处
- **现象**：UBSan 报 `null argument passed to ‘memcpy’`（非空属性违反），落在

## E-25 memenv 的 `rename` 不是 `rename(2)`：自改名释放后继续用、覆盖打开中的目标会丢
- **现象**：新写的 `db.MemenvRenameSemantics` 在 HEAD 上 `rc=139`（SIGSEGV），
  不是断言失败也不是 CHECK 不通过——它在 `free(f->name)` 之后就踩在已释放的
  节点上。另一条（改名到一个仍有打开句柄的目标）不崩，只是**静默丢写入**。
- **定位**：`mem_rename_file()` 只有一行判定 `if (existing != NULL && existing->refs == 0)
  fs_delete_file(&env->fs, existing);`。两个分支各错一次：
  ① `src == dst` 时 `fs_find(dst)` 返回的就是 `f` 本身，于是"删掉 existing"
  把**正在被改名的那个节点**释放了，紧接着 `free(f->name); f->name = strdup(dst);`
  读写已释放内存；② `existing->refs > 0` 时整段跳过，目标节点仍留在命名空间里、
  名字与被改名的节点相同 → 链表里出现两个同名条目，`fs_find` 只看先后次序，
  之后对 `dst` 的读可能落在旧节点上，等于改名没发生。
- **根因**：`mem_remove_file` 早就实现了"仍被打开就延后释放"（unlink 语义），
  但那 12 行是**内联**在 `mem_remove_file` 里的，`mem_rename_file` 没复用，
  自己写了个"只在没人打开时才删"的简化版。POSIX 的 `rename(2)` 无条件替换目标，
  且指向旧 inode 的已打开 FD 继续有效；`rename(a, a)` 是成功的 no-op。
- **修复**：把那段 unlink 提成 `fs_unlink(mem_fs*, mem_file*)`（`refs > 0` 挂
  graveyard，否则就地释放），`mem_remove_file` 与 `mem_rename_file` 共用；
  `mem_rename_file` 先判 `existing == f` 直接解锁返回 ok，其余情况一律
  `fs_unlink(existing)`。顺带给 `mem_file_append` 加 `if (n == 0) return;`
  （E-22 同族：空 slice 是 `{NULL, 0}`，memenv 侧也一样会喂给 append）。
  本仓真实落盘路径不会自己撞进①（leveldb 只把 `.log` 改名成 `.ldb`、
  临时文件改名成 `CURRENT`，src 恒不等于 dst），但 memenv 是**公共 env 后端**、
  测试与调用方直接调 `ldb_env_rename_file`，这就是接口面内的缺陷。
- **验证**：`db.MemenvRenameSemantics` 在 HEAD 上 `rc=139`、本轮代码上 PASS；
  posix 后端同一组形状另用 `dbt_env_write/dbt_env_check_read/dbt_env_child_count`
  三个脚手架断言，两后端由此对齐；L1/L2/L3 全绿（memenv 不落盘，
  黄金比对不受影响）。

## 平台/环境缺陷（N）

### N-1 Windows 进程内 LOCK 重入
- **现象**：`DestroyDB`（数据库仍打开时）报 LOCK 已被占用。
- **根因**：leveldb POSIX 后端的 fcntl 锁是**进程级**，同进程二次
  加锁成功；我的 Win32 实现用共享模式为 0 的 CreateFile，同进程
  第二个句柄也失败。
- **修复**：环境内维护锁表（文件名 → 句柄 + 计数），同进程重入
  直接成功。

### N-2 memenv 无法删除打开中的文件
- **现象**：DestroyOpenDB 删 MANIFEST 报 "file is open"。
- **根因**：memenv 移植时拒绝了 refs>0 的删除；leveldb memenv 与
  POSIX 语义允许 unlink（句柄继续有效，命名空间立即消失）。
- **修复**：实现"分离 + 墓园"：文件立即从命名空间摘除，对象保留
  到最后一个句柄关闭（env 销毁时统一释放）。

### N-3 打开中的文件无法删除（Win32）
- **修复**：所有 CreateFile 调用加 `FILE_SHARE_DELETE`（与 leveldb
  的 env_windows 行为一致），使删除打开中的表文件生效。

### N-4 POSIX 互斥量需递归
- **背景**：memenv 的 Schedule 内联执行后台任务 → 在持锁状态下
  重入 `impl->mutex`。Windows CRITICAL_SECTION 天然递归可工作；
  pthread 默认锁在 Linux 上会死锁。
- **修复**：`port.c` 的 POSIX mutex 改用 `PTHREAD_MUTEX_RECURSIVE`。

### N-5 env_posix.c 缺失
- **背景**：Makefile 在非 Windows 平台引用 `env_posix.c` 但文件未写。
- **修复**：补齐完整 POSIX 实现（pread/write/fcntl 锁/nanosecond
  日志时间戳）。**注意：该文件未在 Windows 开发环境中执行过，
  属于未经测试代码**（在 doc/06 中跟踪）。

### N-6 info logger 的 FILE* 永不归还（doc/06 P0-9）
- **现象**：官方 `leveldb/db/c_test.c` 在原生 Windows 后端的 filter
  阶段报 win32 error 32（`SHARING_VIOLATION`）：`DestroyDB` 之后在同
  一路径重开失败。
- **定位**：`ldb_env_new_logger` 打开的 `FILE*` 只随进程退出被回收；
  POSIX 允许 unlink 一个仍打开的文件，所以同一份代码在 MSYS2 上
  全绿——这个差异只在 Windows 上暴露。用"关库 → DestroyDB → 重开"
  最小化复现后确认残留的正是 `LOG`/`LOG.old` 句柄。
- **根因**：`ldb_logger` 没有销毁钩子，`db.c`/`repair.c` 只能
  `free(logger)`，把 env 在 `new_logger` 里取得的 OS 资源漏掉了。
- **修复**：`ldb_logger` 增 `destroy` 函数指针，`env_win`/`env_posix`
  在其中 `fclose` 后释放（对齐 `~POSIXFileLogger`：`FILE*` 归 logger
  所有），`env_mem` 释放其 buffer；调用点统一走 `ldb_logger_destroy`。
- **验证**：`api_extra.DestroyDbThenReopenInSameProcess`（同一进程内
  3 轮 关库 → DestroyDB → 重开 → 确认已清空 → 再写 → 压缩）。负向
  对照：去掉 `fclose` 后该用例恰好在 DestroyDB 处失败，且全量套件
  进一步崩在 `c_api.ApproximateSizes`。

### N-7 POSIX 判据只认 `-cygwin`，而 MSYS2 报的是 `-msys`（doc/09 §3）
- **现象**：`scripts/build_official.sh` 在 MSYS2 登录 shell 里 `exit 2`，
  报 `Expected a POSIX compiler ... got x86_64-pc-msys`。
- **根因**：`build_official.sh` 与 `run_interop.sh` 用枚举式判据
  `*-cygwin`/`*linux*` 认"POSIX 编译器"。MSYS2 的 msys 层是 Cygwin 的
  fork，但它的 gcc 报 `x86_64-pc-msys`。两种拼法都真实存在过。
- **修复**：三处判据统一为 `*linux*|*-cygwin|*-msys`；`run_sanitizers.sh`
  的"Windows 家族但不是 clang"早退守卫同样补 `*msys*`。
- **验证**：改后 MSYS2 三条腿全 `rc=0`；Cygwin 仍走 `*-cygwin` 分支，
  旧通路不受影响。**引擎侧从未中这个招**——`Makefile` 用的是排除法
  （三元组含 `mingw`/`windows` 才走 Win32），所以后端一直选得对。
  教训：判"是不是某平台"用排除法，别手抄肯定式清单。

### N-8 `export PATH=/usr/bin:/bin` 把 git 也一起扔了（doc/09 §3）
- **现象**：`git: 未找到命令`，`rc=127`——脚本连第一条断言都没到。
- **根因**：PATH 被硬钉成两个目录（初衷是防命名空间串味的 gcc），而
  MSYS2 默认安装不含 git，钉死 PATH 等于钉死"没有 git"。
- **修复**：`export PATH=/usr/bin:/bin${PATH:+:$PATH}`（msys 的 `/usr/bin`
  仍在最前，继承来的 PATH 留作尾部兜底），并加 `command -v git` 前置检查，
  缺失时给三家包管理器的命令而不是 rc=127。`run_golden.sh` 同改——它自己
  钉完 PATH 才调子脚本，只改被调用方没用。
- **验证**：装 git 前 `rc=127`、装后 `rc=0`；`PATH=/nonexistent` 下新守卫
  确实吐提示并 `exit 2`。

### N-9 "官方源码被改动"守卫把嵌套子模块的指针漂移算成改动（doc/09 §3）

### N-10 缺 `g++` 时的提示指向一个脚本随后会拒绝的包（doc/09 §3）
- **现象**：提示写 `MSYS2: pacman -S mingw-w64-ucrt-x86_64-gcc`。

  提供这个路径"。`run_interop.sh` 同一处同改（顺把它漏在 stdout 的错误改到

### N-11 `env_posix.c` 的头部注释是一个过期且方向危险的断言（doc/09 §3）
- 注释写"本后端从未在本项目的开发环境里执行过，按 best-effort 看待"。
  MSYS2 与原生 Linux 早已实机跑通，这句话会让后来人不敢用这条通路。
  改为陈述"在原生 Linux(glibc) 与 Windows 的 POSIX 仿真层(msys) 上都执行过"，
  并点出真实约束：后端由 `!defined(_WIN32)` 选定，所以任何"定义 `_WIN32`
  却提供 POSIX 语义"的主机必须在那里被排除，否则会静默链上 Windows Env。
  本轮把这个约束变成了测量：MSYS2 与 Cygwin 的 gcc 都不定义 `_WIN32`。

### N-12 本地化 shell 里 `grep 'warning:'` 恒为 0（doc/09 §3）
- **现象**：收尾复跑三条 Windows 通路后数警告，得到 msys 0 / Cygwin 6 /
  w64devkit 8。"MSYS2 零警告"看着像一个真实的平台差异。

- **根因**：判据依赖编译器诊断的**英文拼写**却没有固定 locale。与

- **修复**：代码不动（这 6 条早记在 P3-3）。文档侧把"数警告先 `export

### N-13 `run_cross_backend.sh` 缺 TMP 守卫，坏环境伪装成后端不一致（doc/09 §5）

  下探测通过、整条腿照旧 `rc=0`。

### N-14 参考库缓存跨命名空间串档（doc/09 §3）
- **现象**：收尾复跑 MSYS2 的黄金腿，在建完 kvdb、编完驱动之后死在链接：
  `undefined reference to '__pthread_normal_mutex_initializer_np'`，出处是
  `build/interop/official/lib/libleveldb_official.a(db_db_impl.cc.o)`，脚本
  报 `official link failed`。而**同一份脚本、同一台机器一小时前刚跑过
  rc=0**，所以看上去像是 MSYS2 的 POSIX 线程支持莫名坏了。
- **定位**：`nm -u` 确认归档里确实有这个未定义符号，而 `/usr/lib/libpthread.a`
  中该符号出现 0 次——它既不是 msys 的、也不是 msys 缺的。目录时间线给出答案：
  `lib/libleveldb_official.a` 的 mtime 是 01:09（Cygwin 那一轮），缓存标记却有
  两个空文件并存：`.built-…-13.3.0-13.3.0`（00:55，msys）与
  `.built-…-14-14`（01:09，Cygwin）。
- **根因**：`build_official.sh` 的缓存三元组里少了最关键的一维。标记文件名
  只带 pin 的提交号与两个编译器版本号——**上一行明明已经算出 `TRIPLE` 却没被
  用进去**；输出路径又是所有命名空间共享的单个 `build/interop/official/`；
  命中判据是"标记文件存在"，而不是"这个归档是那次构建的产物"。msys 与 Cygwin
  在运行时互不可见，却在这一棵磁盘树上完全可见，于是 MSYS2 拿到了 Cygwin 编的
  参考库。同一符号在 Cygwin 里存在、在 msys 里叫别的名字，链接期才暴露。
- **修复**：① 输出按三元组分目录（`build/interop/official/<triple>/`，含
  `obj/`、`include/`、`probe/` 与生成的 `port_config.h`），标记文件名也带
  三元组；② 标记内容从"时间戳"改成"归档摘要"，命中前重算比对——中断在
  `ar` 与 `touch` 之间的构建、手工换掉的归档，都不再能被一个空文件担保；
  ③ 没有 `sha256sum`/`shasum` 时写入永不匹配的 `unverified`（⇒ 每次重建），
  而不是判为缓存有效，与 `run_golden.sh` 的字节判据同一条 fail-closed 规则
  （doc/08 §5 第 4 条）。
- **验证**：把 Cygwin 的旧产物迁到新目录后，Cygwin 侧输出
  `reusing cached official build`（顺带证明缓存命中路径本身可用）；**负向
  对照**：给归档追加一个字节再跑 → `cache stamp does not match the archive;
  rebuilding`，重建后摘要确实变了，第三次跑回到 `reusing`；MSYS2 建出自己的
  `x86_64-pc-msys/`（39 秒）后黄金腿 rc=0（109 PASS / 33 SAME / 1 DIFF / 1
  INFO，唯一 DIFF 是 `levels` 的布局差异、判据按 INFO 处理），
  `RUN_C_TEST=1 run_interop.sh` 也 rc=0。留档
  `build/interop/golden-20260920-{021013,021110}`、`run-D7SUdnww`。

### N-15 `make` 在共享对象树上跨命名空间报"Nothing to be done"（doc/09 §3）
- **现象**：N-14 修完后回头查同一类问题——kvdb 自己的对象树是不是也跨命名空间
  共享。在 MSYS2 刚 `make` 完的树上，用独立 Cygwin 跑 `make -n`：
  `make: Nothing to be done for 'all'.` 而 `build/libleveldb.a` 此刻是 msys 的
  产物。
- **根因**：`OBJDIR` 默认 `build`，四种三元组（`x86_64-pc-msys`、
  `x86_64-pc-cygwin`、`x86_64-w64-mingw32`、`x86_64-w64-windows-gnu`）写出的
  `.o` **文件名完全相同**，而 make 只按 mtime 判新旧，看不见"是谁编的"。只有
  `env_posix.o` 按平台分支出现与否有别，其余对象逐个撞名。
- **影响**：在 Cygwin shell 里 `make` 得到"无需构建"，接着 `make test` 跑的是
  依赖 `msys-2.0.dll` 的 msys 二进制（Cygwin 的 PATH 上没有它，Windows 弹的是
  "找不到 DLL"）；部分重建时更糟——一桶混合对象，ld 报出的未定义符号读起来
  像引擎缺陷。N-14 是同一件事在参考库那一侧的表现。
- **修复**：`$(OBJDIR)/.target` 记录产出这批对象的三元组（在 `$(LIB)` 的 recipe
  里写），Makefile 解析期与当前 `$(CC) -dumpmachine` 比对，不一致直接
  `$(error …)` 并指名 `make clean`；`clean` 目标本身豁免（它就是补救手段），
  并从 `clean` 里删掉这个文件。按 `OBJDIR` 记账而不是按仓库根，所以
  `run_sanitizers.sh`（`build/san`，动手前 `rm -rf`）与 `run_cross_backend.sh`
  （`$RUN/obj/<name>`，每次全新）天然不受影响。脚本侧同源：
  `run_golden.sh`/`run_interop.sh` 吃现成归档时，除 mtime 外再比 `.target` 与
  本 shell 的三元组；没有 `.target` 只表示"早于该记录"，不作判据。
- **验证**：Cygwin 的 `make` 与 `make -n` 在 msys 树上都 `rc=2`，
  `Makefile:72: *** build/ holds objects built for x86_64-pc-msys but gcc
  targets x86_64-pc-cygwin; run 'make clean' before switching toolchains.`；
  w64devkit 的 gcc（第三种三元组）同样拦下，`make clean` 正常通过；
  Cygwin 与 w64devkit 各自 clean 重建后仍是 127/127，`.target` 分别为
  `x86_64-pc-cygwin` / `x86_64-w64-mingw32`；MSYS2 shell 里对着 Cygwin 建的树
  跑那两条脚本，各自 `rc=2` 并给出同一句 remedy（留档
  `build/interop/golden-20260920-021054`）。
- **边界**：这条守卫把"三元组"当成"运行时命名空间"，而两者并非一一对应——
  见下面的 N-19。

### N-16 `probe_lock` 的单条 `local` 让 posix 半边去锁 windows 的树（doc/09 §10）
- **现象**：本机复跑跨后端这条通路，看留档时发现 `lock-posix/*.log` 里每一条拒绝
  信息写的都是 `db-windows/lockprobe/LOCK`。
- **根因**：`local who=$1 mode=sst-bigblock n=8 db="db-$who/lockprobe" i` 写在
  一条声明里。bash 先把这条声明的**所有**字展开完，再逐项赋值，所以
  `db` 拿到的 `$who` 是外层的那个——上面模式循环 `for who in posix windows`
  跑完留下的最后一个值 `windows`。最小复现：`who=windows` 时同一条声明给出
  `db-windows/x`，拆成两条 `local` 才得到 `db-posix/x`。
- **影响**：两个探针共用一棵目录。`probe_lock posix` 先 `rm -rf` 掉 windows
  那侧刚用完的树、再用 posix 二进制重新播种，于是（a）"POSIX 后端在自己的树上
  拒绝第二持有者"当时测的其实是一棵名字叫 `db-windows` 的 posix 树；（b）留档里
  `db-windows/lockprobe` 最终装的是 posix 写的字节，名字与内容不符；（c）两个
  探针不是互不相干的两次实验。结论方向没有反（播种方与读取方始终是同一个二
  进制），但判据的归属被记错了。
- **修复**：拆成 `local who=$1` / `local mode=… n=8 i` / `local db="db-$who/…"`
  三条；顺带把 `i` 也收进函数作用域。
- **验证**：修后重跑（`build/interop/cross-20260920-105654`，`rc=0`），
  `lock-posix/*.log` 全部指向 `db-posix/lockprobe`、`lock-windows/*.log` 指向
  `db-windows/lockprobe`，两侧各 5 开 / 3 拒，逐字节比对仍是 33 SAME / 0 DIFF。
  改前的那一次留在 `build/interop/cross-20260920-104625`（同一条通路，`rc=0`，
  只是 `lock-posix/*.log` 里句句写着 `db-windows/lockprobe`）——两棵目录树就是
  这条缺陷的改前/改后对照，`build/` 不入库，换机器须重跑。

### N-17 原生 Windows 编译器"一字未吐"就退出，被 TMP 守卫误诊（doc/09 §10）
- **现象**：本机 `TMP` 已经是 Win32 形状（`D:\ProgramFiles\msys64\tmp`），
  N-13 的编译器探针仍失败，并打印"`TMP` 需要 Win32 形状"这一串 remedy；而它
  引用的那份 `logs/tmpprobe.log` 是 **0 字节**（该次留档
  `build/interop/cross-20260920-104431`，2KB，只装了这份空日志与探针源）。
- **定位**：手工重放探针。`/mingw64/bin/gcc.exe -c p.c -o p.o` 在
  `PATH=/usr/bin:/bin` 下 `rc=1` 且 stderr 全空；`gcc -v` 显示它把活交给
  `lib/gcc/x86_64-w64-mingw32/16.1.0/cc1.exe`，而 cc1.exe 的 DLL 依赖
  （`libgcc_s_seh-1`、`libwinpthread`、`libzstd` …）全在 `/mingw64/bin`，Windows
  只按 PATH 找 → 子进程根本起不来。把 `/mingw64/bin` 放进 PATH，同一命令
  `rc=0`。真·TMP 问题长得不一样：gcc 会打
  `Cannot create temporary file in C:\Windows\: Permission denied`（本机实测 `rc=3`）。
- **根因**：N-13 把"探针失败"唯一归因于 `TMP`，但探针的失败面至少两种（scratch
  目录不可用 / 编译器自身起不来）。脚本按第一种解释报，于是在环境其实正确的
  机器上给出一句错的处方——正是它自己那条"别把环境问题读成后端不一致"的反面。
- **修复**：① 探针之前把 `$(dirname "$CC_WIN")` **追加**到 PATH 末尾（追加不是
  前插：`make`/`sed`/`find` 仍必须由 `/usr/bin` 提供）；② 失败诊断按"有没有吐出
  字"分岔——吐了字照旧报 TMP，一字未吐就指名 cc1.exe 起不动、它的 bin 目录才
  是 DLL 的来源，并明说这不是 TMP 问题。探针的退出码单独存 `probe_rc`，因为
  进到分支里 `$?` 已经被 `[[ -s … ]]` 覆盖。
- **验证**：不再手工改 PATH 的调用形式下整条通路 `rc=0`（上一条留档即证）。
  N-13 原有的判据没被削弱：`TMP=C:\Windows` 下仍 4 行内给出编译器原文加 TMP
  处方并 `rc=2`。**新分支的文本本身没被跑到过**——要触发它得让 `-dumpmachine`
  能应答而 `cc1.exe` 起不来，而那恰好是自愈修掉的那种形状；一个只拷了
  `gcc.exe` 的空目录会在更早的三元组断言处退出（实测），所以这一支是按
  推理保留了兜底，不是按测量验证过的。

### N-18 锁探针把"任何带 lock 字样的失败"算成合法拒绝（doc/09 §10）
- **现象/根因**：分类判据是 `grep -qiE 'LOCK|…'`，没有词边界。而被探测的库
  就叫 `lockprobe`、负载就叫 `sst-bigblock`，LevelDB 自己的损坏信息里还带
  "block"。于是崩溃、缺失文件、数据损坏都会被记成 `refused`。
- **为什么严重**：`refused > 0` 是这条探针唯一的反向守卫——脚本注释自己写着
  "零冲突即 FAIL，因为 8 个并发里通常约一半碰撞"。一次真缺陷只要顺带提一句
  路径，就能把它需要的拒绝次数凑满，然后以"两种后端都真的拒绝了第二持有者"
  的面目通过。P2-6 的闭环判据因此是虚的。
- **修复**：匹配引擎真正拒绝的那个文件名——`<db>/LOCK` 后面紧跟 `:`、空格或
  `(`，再保留三条 errno 短语与 `win32 error 32`。
- **负向对照**（四条样本，改前/改后各判一次）：两条真拒绝改前改后都是
  `REFUSED`；`Corruption: error in middle-level block` 与
  `IO error: db-windows/lockprobe/000005.ldb: No such file or directory`
  改前被判 `REFUSED`、改后落回 `unexplained rc=… → FAIL`。修后整条通路仍
  `rc=0`，两侧各 5/3，说明真拒绝没有被新表达式漏掉。
- **顺带一条读数注意**：windows 那侧的拒绝信息里夹着 GBK 的本地化 Win32 文案，
  日志按二进制看待，`grep` 会打 `Binary file … matches`；判据本身不受影响
  （匹配即 `rc=0`），但人去数这些日志时要带 `-a`，否则看不到原文。

### N-19 `.target` 记的是三元组，不是运行时命名空间（doc/09 §7 W6）
- **前提**：N-15 的守卫假设"三元组 ↔ 运行时命名空间"一一对应。
- **反例就在仓库自己的两份记录里**：本机 MSYS2 的 msys 层 gcc 15.2.0 报
  `x86_64-pc-cygwin`（doc/08 §8.1），独立 Cygwin 的 gcc 14.4.0 报的也是
  `x86_64-pc-cygwin`（doc/09 §4.3 的探针表），而这两家的对象文件互相解不开
  ——那正是 N-14 的根因。所以在报 `-msys` 的 MSYS2 新一代上守卫是精确的，在报
  `-cygwin` 的这一代上它会放行"Cygwin 直接复用 msys 建好的树"，退回 N-15 修掉
  的那个表现（`Nothing to be done`，随后跑一个加载不到 `msys-2.0.dll` 的二进制）。
- **本机测不了**：这台机器没有独立 Cygwin，装它不在授权范围内（README 的
  `_tools/w64devkit/` 也不存在，MinGW-w64 那一支由 MSYS2 的 `/mingw64` 代表）。
  所以这一条**只有推理，没有实测**。
- **可行的补法**（未落地，登记为 doc/09 §7 的 W6）：键里再加一维**由编译器自己
  回答**的运行时标识。本机实测 `gcc -dM -E -x c /dev/null` 给出
  `__MSYS__` **和** `__CYGWIN__` 两个宏；独立 Cygwin 的 gcc 只有后者——
  `__MSYS__` 是 MSYS2 那支 fork 加的，不随 `MSYSTEM`、`PATH` 之类的调用方变量
  变，正好是缺失的那一维。取法例如
  `RUNTIME := $(shell $(CC) -dM -E -x c /dev/null 2>/dev/null | grep -q __MSYS__ && echo msys)`，
  只附加到 `*-cygwin`/`*-msys` 这类会撞的三元组上，免得给 mingw 分支添噪声。
  两点诚实的边界：`"Cygwin 不定义 __MSYS__"` 这一半是**推理**（本机没有 Cygwin，
  按宏出处判断），没测过；改一次会让所有现存 `.target` 与新键不匹配一次，而报错
  文本已经指名 `make clean`，代价可以接受。
- **一条已经排除的取法**：别用 `$OSTYPE`。本机在 MSYS2 的 shell 里实测
  `bash` 与 `/bin/sh` 都报 `OSTYPE=cygwin`（这一代 MSYS2 的 bash 就是以
  `x86_64-pc-cygwin` 构建的），与独立 Cygwin 同串，分辨不出来；`MSYSTEM` 也不
  能用——它是调用方设的，Git Bash 里是 `MINGW64` 而 `/usr/bin` 根本没有 gcc。

## 过程性事故（非代码缺陷）

1. **perl/sed 多行正则失控（3 次）**：贪婪匹配把 test_util.c 膨胀到
   12884 行、test_skiplist.c 到 8185 行、test_table.c 多处错乱，
   全部重写。**规程修改**：源码批量修改只用 Edit 工具或单行替换。
2. **bash heredoc 体积截断（3 次）**：单条命令约 12KB 上限，超限
   静默截断导致 version_set.c / db.c 尾部损坏，靠 `tail`/`grep` 发现
   后用小块重写。**规程修改**：大文件追加分块 ≤8KB。
3. **占位代码残留**：初版若干文件留有"placeholder"注释体，编译器
   与测试逐步逼出并清理（如 write_batch 的 inserter、repair 的
   比较器适配）。
4. **验证侧的三处假阳性**（记下来免得重复排查，都不是引擎缺陷）：
   ① clang64 shell 未设 `TMP`/`TEMP`/`TMPDIR`，`GetTempPathA` 逐级回落
   到 `C:\Windows`，18 个真实文件系统用例因无法建目录全红；
   ② 黄金驱动里 `fnv(h, leveldb_iter_key(it, &kn), kn)` 的实参求值
   顺序未定，出参可能读到上一轮的长度，一度表现为"跨引擎摘要不一致"；
   ③ 原生 Linux 首轮黄金比对没传 `KVDB_LIB`，静默链上 `build/` 里两周前的
   `libleveldb.a`，报出 4 个"Linux 专属缺陷"（`sst-bloom`/`sst-bigblock`
   SIGSEGV、`edge` 触发 `block.c:184` 断言、`tomb` 点查 NotFound）——
   用当前源码重建后同一条腿 rc=0。③ 的教训不是"手滑"而是**脚本没有守卫**：
   `run_golden.sh`/`run_interop.sh` 现已在归档比 `src/`、`include/` 旧时直接
   `exit 2`，并对该守卫做了负向对照（把归档 `touch` 到过去时间后两条腿都拒绝）。
   三处都改在测试/脚本侧并留了注释。
5. **验证脚本自己咬人**：一次 `rm -rf build` 连带删掉了当轮的黄金比对
   留档；`run_sanitizers.sh` 初版把 `rm -rf "$OBJDIR"` 放在 clang 存在性
   检查之前，一次误运行就清空了 sanitizer 留档。**规程修改**：证据目录
   一律放在被删对象树之外（`build/san-runs/`），并且任何删除动作都必须
   排在参数/环境校验之后。
