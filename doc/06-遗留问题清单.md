## 复查结论

- **正确性**：核心路径（写/读/压缩/恢复/快照/迭代/修复）均有测试
  直接覆盖；P0-4（repair 序列号）是本次复查发现的唯一真实数据正确性
  缺陷，已修复并验证。
- **健壮性**：损坏数据恢复类路径是当前最大的验证空白（P1-2/P2-3），
  也是与 leveldb 测试集差距的剩余部分。
- **可移植性**：Windows 路径经过 92 用例验证；POSIX 路径代码完备但
  需要一次真实的 Linux 构建验证（P2-1）。

### 2026-09-19 跨引擎二进制兼容性复核

- **接口**：`include/leveldb/c.h` 声明的 68 个函数与官方头文件逐签名
  一致且全部导出；未经修改的官方 `leveldb/db/c_test.c` 直接链接 kvdb
  通过（create_objects…repair/filter/cleanup 全组 PASS）。
- **格式（写侧）**：9 种确定性负载下两引擎产出的每一个文件
  （`.ldb`/`.log`/`MANIFEST`/`CURRENT`，共 33 个）逐字节相同；这一轮
  发现并修复了 P0-7（footer padding 未清零）——修复前 kvdb 的 `.ldb`
  尾部含堆残留，是"看起来兼容、实际差 20 字节"的典型。
- **格式（读侧）**：两引擎交叉读对方的目录（含 `levels` 模式的多层表），
  点查摘要 + 正/反向全扫描摘要四路完全一致。
- **staged 修复复核**：`leveldb_get` 的 NotFound 语义与错误保留、
  `bloom_internal` 的 state 类型混淆、Get 释放 DB 互斥、压缩输出文件
  双重销毁、`ldb_status` 所有权与泄漏，均与官方 `c.cc`/`db_impl.cc`
  行为一致，且每项都有对应新用例。
- **残余**：P2-7（压缩调度差异）、P2-8（snappy 字节级未比对）、
  P2-9（本机无 sanitizer 运行时）是本轮未能闭环的三项。
