# 06 — 遗留问题清单

本文档是在交付评审（2026-09-14）中对全部代码逐文件复查后整理的
遗留问题。分四级：**P0 已在评审中修复**、**P1 功能缺口**、
**P2 风险与未验证项**、**P3 质量与优化**。

---

## P0 — 评审中发现并已当场修复

| # | 问题 | 修复 |
|---|---|---|
| 0-1 | `ldb_snapshot_list_smallest` 在头文件声明但从未定义（潜在链接陷阱） | 补实现：返回最老快照序列，空链表返回 kMaxSequenceNumber |
| 0-2 | POSIX 互斥量非递归：memenv 的内联 Schedule 会在持锁状态下重入 `impl->mutex`，Linux 上死锁（Windows CRITICAL_SECTION 天然递归所以测试未暴露） | `port.c` 改用 `PTHREAD_MUTEX_RECURSIVE` |
| 0-3 | `env_posix.c` 在 Makefile 中被非 Windows 构建引用但文件不存在 | 补写完整实现（见 P2-1 的验证要求） |
| 0-4 | **repair 未恢复 last_sequence**（固定写 1）：修复后新写入会拿到比表中现存键更小的 sequence，导致新值被旧版本遮蔽——真实数据正确性缺陷 | scan_table 统计各表最大 sequence 并取全局最大写入 edit |
| 0-5 | c.h 转换头中 `leveldb_compact_range` 的 NULL 语义与官方 c.cc 一致性存疑 | 对照官方 c.cc 确认"NULL 指针 → 空 Slice 语义"，实现已一致，无需改动 |
| 0-6 | （2026-09-14 复测新增）test_skiplist.c 的 `skip_insert` 将 skiplist 节点 key 指入会 realloc 的 `storage` buffer，缓冲增长后旧节点 key 悬空 → 全量回归约 1/4 概率在"不允许重复插入"断言处失败；`InsertAndLookup` 因自行预留容量而从未暴露。引擎无此问题（memtable 将 key 拷入 arena） | `skip_init` 预留 1MB 容量，保证测试期间 storage 不再 realloc；修复后连续 10 次全量回归通过 |

## P1 — 功能缺口（有意未做，按优先级排序）

| # | 缺口 | 影响 | 建议 |
|---|---|---|---|
| 1-1 | `Options::reuse_logs` 未实现（恒为 false） | 打开时不复用旧 MANIFEST/WAL，只影响恢复后的首写性能，不影响正确性 | 实现 `ReuseManifest` + `RecoverLogFile` 的 reuse 分支（leveldb 各约 30 行） |
| 1-2 | 故障注入 Env（SpecialEnv：可控读写失败、损坏注入、计数延迟）未实现 | db_test / corruption_test 中约 20 个损坏恢复类用例未移植 | 在 ldb_env 上加注入钩子层 |

| 1-5 | repair 为简化版：不做 leveldb 式 file checksum 复核、不重建压缩层级（全部平铺 L0） | 修复后首次压缩成本略高；正确性无损 | 对齐 db/repair.cc 的 TableInfo/在役文件元数据复核 |

## P2 — 风险与未验证项

| # | 项 | 风险 | 验证方法 |
|---|---|---|---|
| 2-1 | **env_posix.c 从未在 POSIX 环境执行过**（开发机为 Windows） | 可能有编译错误或平台 API 细节问题（如 O_CLOEXEC 缺失、目录 fd 处理） | 在 Linux/macOS 上 `make && make test`，重点跑 db/c_api 组 |
| 2-2 | **并发正确性未压测**：写者队列、后台压缩与并发 Get 的交错只被单线程测试间接覆盖 | 理论上锁协议与 leveldb 一致，但缺多线程压力证据 | 移植 db_test 的 MultiThreadTest（读写双线程 + MemTableTrash） |
| 2-3 | 损坏数据路径覆盖薄：log 回放损坏（MaybeIgnoreError）、paranoid_checks、块 CRC 失败恢复只在单元级验证 | 损坏库的实际恢复行为与 leveldb 可能有细节差异 | 实现 P1-2 后移植 corruption_test |
| 2-4 | log reader 的 `initial_offset > 0` 分支只过了代码审查（测试全部用 0） | dumpfile 类工具若用非零偏移可能遇到边界 bug | 补 log_test 的 SkipToInitialBlock 系列 |
| 2-5 | 大值路径：>4096 字节的键在 write_batch 回放中走堆缓冲，>块大小的值未专项测试 | 潜在边界条件 | 补大值往返用例 |
| 2-6 | Windows 锁实现是"进程内计数 + 独占打开"，跨进程冲突依赖共享模式语义 | 与 fcntl 的区域锁语义有差异（如同进程多 DB 实例共用目录） | 多进程互斥专项测试 |

## P3 — 质量与优化（不影响正确性）

| # | 项 | 说明 |
|---|---|---|
| 3-1 | info_log 的 FILE* 在 DB 关闭时不 fclose（进程退出由 OS 回收）；memenv logger 的缓冲同样滞留 | 加 logger 销毁钩子即可 |
| 3-2 | Win32 Env 每次 append 直接 WriteFile（无用户态缓冲） | leveldb env_windows 有缓冲；高吞吐场景可加 64KB 缓冲 |
| 3-3 | `-Wignored-qualifiers` / `-Wmissing-field-initializers` 两类无害警告未清零 | 前者源于 c.h 风格的 const 返回值，后者是指定初始化器简写 |

| 3-5 | `ldb_buffer_remove_prefix`（memmove 语义）在 log.c 重写后已无调用方 | 保留作通用工具，或移除 |
| 3-6 | version_set.c 中两个冒泡排序（L0 新旧排序、Builder added 排序）为 O(n²) | 文件数场景下无碍，大层级可换 qsort |
| 3-7 | `leveldb/` 参考克隆留在仓库内 | 仅作文档对照，不参与构建；可在正式发布时移除或转 submodule |

## 复查结论

- **正确性**：核心路径（写/读/压缩/恢复/快照/迭代/修复）均有测试
  直接覆盖；P0-4（repair 序列号）是本次复查发现的唯一真实数据正确性
  缺陷，已修复并验证。
- **健壮性**：损坏数据恢复类路径是当前最大的验证空白（P1-2/P2-3），
  也是与 leveldb 测试集差距的剩余部分。
- **可移植性**：Windows 路径经过 92 用例验证；POSIX 路径代码完备但
  需要一次真实的 Linux 构建验证（P2-1）。
