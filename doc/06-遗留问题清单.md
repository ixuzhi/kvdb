## 复查结论

- **正确性**：核心路径（写/读/压缩/恢复/快照/迭代/修复）均有测试
  直接覆盖；P0-4（repair 序列号）是本次复查发现的唯一真实数据正确性
  缺陷，已修复并验证。
- **健壮性**：损坏数据恢复类路径是当前最大的验证空白（P1-2/P2-3），
  也是与 leveldb 测试集差距的剩余部分。
- **可移植性**：Windows 路径经过 92 用例验证；POSIX 路径代码完备但
  需要一次真实的 Linux 构建验证（P2-1）。

### 2026-09-19 原生 Linux（glibc）环境复核

第一次在真正的原生 Linux（Debian 12 / glibc 2.36 / gcc 12.2）上把全部腿跑一遍，
闭合 P2-1 的一半（macOS 仍待实机）。四条腿全绿：L0 构建 + 127 用例、L1 逐字节
黄金比对（109 PASS + 33 文件相同）、L2 互操作 65 阶段 + 未修改的官方 `c_test`、
L3 gcc 版 ASan/UBSan 全链零报告。逐条命令、留档路径、为跑通新装的 7 个软件包
与卸载方法、以及延后项都在专档 **doc/08**。

- **新增缺陷 P0-10**：`get_range2` 把 `NULL + 0` 交给 `memcpy`，glibc 的 `nonnull`
  声明使 UBSan 判罚——官方 C++ 用 `std::vector` 合并，这条 UB 是 C 重写引入的；
  clang64 腿看不见它。这正是"非要原生 Linux 不可"的那类证据。
- **能力增量**：Linux 的 gcc 自带 asan/ubsan/tsan 三套运行时，`libasan.so.8` 还带
  LeakSanitizer——Windows 腿"只能 clang、且查不了泄漏"的两条限制在这里都不成立。
  `run_sanitizers.sh` 现按宿主自动选编译器。
- **主动延后**（不是能力缺失，逐项带"怎么补"）：T1 LSan 泄漏维度、T2 TSan +
  并发压测、T3 行/分支覆盖率、T4 多进程锁专项（P2-6）。见 doc/08 §9。
- **P2-8 首次实测**：装 snappy 后压缩块**不**逐字节相同（kvdb 大 3.4%）但**双向可解**、
  摘要一致——差异从"未知"变成"已知且只影响压缩率"。仍未进正式比对。
- **两个新记录的 harness 陷阱**（P2-12）：`make CFLAGS=` 会吞掉 `+=` 追加；
  跨引擎腿会静默链接陈旧归档（本轮真实地把旧库的 4 个症状误读成 Linux 专属缺陷，
  才想起没传 `KVDB_LIB`）。两处都已在脚本里加守卫并做了负向对照。
- **Windows 侧回归已完成**：`Makefile` 的 `SANFLAGS` 通道与脚本的跨平台改造先只在
  Linux 上实测过，随后在本机（Windows 10 + MSYS2 三条通路：MSYS gcc 15.2 / MINGW64
  gcc 16.1 / clang64 22.1）逐条复跑，全绿——127 例 ×2、clang64 ASan/UBSan `rc=0`
  （127 例 + 官方 c_test 16 阶段 + 10 负载 create/verify，零报告）、golden `rc=0`
  且 `results.tsv` 与 P0-10 之前那轮**逐行相同**（互操作 65 阶段全 `rc=0`）。
  风险点与实测结论逐条在 doc/08 §8；这轮复跑又抓到并已修两处脚本缺陷（P2-12③）。

### 2026-09-20 Windows 工具链矩阵复核（mingw / msys2 / cygwin）

把"Windows 已验证"这句话重新变成一台别的 Windows 机器上可复现的结论。结果是
**引擎零改动、127/127 在每一支 Windows 家族编译器上照旧**，而验证装置在九处
因为把环境前提当成事实而失效（N-7…N-15，P2-12⑤–⑧）。逐条命令、安装与卸载、
负向对照都在专档 **doc/09**。同日**第二台** Windows 机器（另一代 MSYS2：msys 层
报 `x86_64-pc-cygwin` 而不是 `-msys`；MinGW-w64 由 `/mingw64` 而非 w64devkit 代表）
把这台机器能跑的几条通路复跑了一遍——127/127、跨后端 `rc=0`（58 PASS / 33 SAME /
0 FAIL 同数）、clang64 内存安全 `rc=0` 且跨通路摘要逐字符相同——并再抓到四条同类
装置缺陷（N-16…N-19，P2-12⑨–⑫，doc/09 §10）。上面那批留档只存在于跑它的那台
机器上（`build/` 不入库），换机器须重跑，这一遍就是那份"换一台也成立"的证明。

- **工具链从四条变五条**：新增独立 Cygwin（gcc 14.4.0 / cygwin1.dll 3.6.10），
  首轮 build_official + 黄金 + 互操作 + 官方 `c_test` 全绿。这一条把 P2-1 那个
  从 2026-09-14 起就挂着"Cygwin"字样的说法真正兑现了。
- **新增第 5 条脚本腿** `run_cross_backend.sh`：同一台机器上用 POSIX 三元组和
  Windows 三元组各建一份引擎，要落盘字节逐字节相同、四方向读取摘要全等。这补的是
  一个结构性空白——黄金比对与互操作**全部**由 `env_posix.c` 产出，`env_win.c`
  的字节从来没收过任何比对。9/9 模式、33 文件 SAME、58 PASS、0 FAIL。
- **P2-6 跨进程一半闭环**：8 并发 `verify` 在两种后端上分别得到 5/3 与 4/4 的
  "开成/被拒"，拒绝原因分别是 `win32 error 32` 与 `EAGAIN`。判据含"零争用即
  FAIL"，所以这个 PASS 不是运气。**两条限定（N-16、N-18，已在装置上修掉）**：
  当时"posix 侧"那一次其实锁的是名叫 `db-windows/lockprobe` 的目录（播种方与
  读取方仍是同一个二进制，所以结论方向不变），而拒绝的分类判据 `grep -qiE 'LOCK'`
  没有词边界、会被含 "block" 的损坏信息满足——也就是说"至少一次拒绝"这个守卫
  当时可以被一次崩溃凑满。第二台机器修后复跑两侧各 5/3、`rc=0`。同进程多实例
  那一半仍是 W5。
- **sanitizer 通路重装复现**：本机 clang64 曾被卸载，重装后 `rc=0` 零报告；
  并且"Windows 的 gcc 没有 sanitizer 运行时"从推断升级成四支编译器的直接链接
  探针（三支 `cannot find -lasan`，只有 clang 链得上）。
- **一条测量取代了一条推测**：`env_posix.c` 里那句"本后端从未执行过"的注释已
  过期且方向危险（N-11）；曾计划引入 `LDB_PLATFORM_WIN32` 把后端选择从 `_WIN32`
  里解耦，实测 MSYS2 与 Cygwin 的 gcc **都不**定义 `_WIN32`，现有判据本来就是对的，
  于是那次重构**没有做**——这是本轮唯一"查了之后发现不该改"的候选。
- **收尾复跑又抓到两条（N-12、N-13），都出自 `bash -lc` 与 `bash -c` 不是同一个
  环境**：登录 shell 给 `LANG=zh_CN.UTF-8`，于是 `grep 'warning:'` 恒为 0，本轮
  一度据此以为"msys 通路零警告"（真值是 6 条，与 Cygwin 逐条同形）；非登录 shell
  不给 `TMP`，于是只有原生 Windows 那半边构建失败，看上去像两个后端不一致。
  现在复跑清单要求 `export LC_ALL=C`，`run_cross_backend.sh` 也补上了动工前用
  `CC_WIN` 真编一个空文件的试探（doc/09 §9）。
- **最后抓到的是"缓存跨命名空间串档"两处（N-14、N-15），这一对的方向与前面
  七处相反**：前面七处是让脚本**拒绝**了一次好运行，这两处是让脚本**接受**了
  一次坏运行。msys 与 Cygwin 运行时互不可见，磁盘上却共享同一棵 `build/`，
  而两边的缓存判据都只认"文件在"不认"是谁产的"——参考库归档被 Cygwin 那一轮
  覆盖后，MSYS2 的黄金腿照旧 rc=0 地开跑、直到 ld 报出一个看起来像 msys
  pthread 坏掉的未定义符号；`make` 侧则是四种三元组的 `build/*.o` 完全撞名，
  msys 建完之后 Cygwin 的 `make -n` 回一句 `Nothing to be done for 'all'.`。
  现在参考库按 `<triple>/` 分目录、缓存标记的内容是归档摘要（命中前重算，
  没有 sha 工具就写一个永不匹配的哨兵），`$(OBJDIR)/.target` 记录对象的产出者、
  三元组不符时 Makefile 与两条吃现成归档的脚本一起拒绝。**N-14 修完之后的第二遍
  收尾**（doc/09 §9.1）：MSYS2 127/127 + 黄金 rc=0（109 PASS/33 SAME）+
  `RUN_C_TEST=1` 互操作 rc=0 + 跨后端 rc=0，Cygwin 与 w64devkit 各自 clean
  重建 127/127，四处负向对照全部按预期拒绝。
