评估对象：kvdb（纯 C11 重写的 LevelDB 1.23 兼容引擎，G:\code\kvdb）
评估日期：2026-09-25（独立复核轮）
评估方法：见 [doc/11-检查检测评价方法论](11-检查检测评价方法论.md)；
本轮证据 = 三路只读审计 agent + 动态回归 + 跨引擎黄金链 + 已有三轮环境验证记录（doc/07/08/09）。

## 1. 结论摘要

**总体判断：这是一个达到"生产可用起步线"、兼容主张有硬证据支撑、验证装置成熟度显著超出一般移植项目的实现；但"磁盘格式逐字节兼容"这一措辞需要收窄，且格式层存在 4 条高等级缺陷。** C API 兼容与磁盘格式互操作两条核心主张均有直接证据（官方 `c_test.c` 原件 16 阶段直连 PASS；官方写/kvdb 读与反向的逐字节黄金比对 rc=0），146 条用例在 Windows 与 POSIX 双后端全绿。本轮三路独立审计共确认现存缺陷 **16 项引擎级（1 critical / 10 major / 2 high-format / 3 minor）+ 13 项测试装置隐患 + 24 组官方用例覆盖缺口**，其中格式层 4 条高等级 bug（filter 假阴性、count=0 batch 校验缺失、CRC 表初始化竞争、cache NewId 竞争）是本报告相对既有文档的主要增量。

**最需要正视的两类**：① skiplist 的无锁读缺少发布协议（critical，C 内存模型层 UB，x86 上"碰巧工作"）；② filter_block 对损坏 offset 返回"不存在"（F-1，读路径可漏掉真实存在的 key）——两者都属"正常测试永绿、边界条件致命"型。与之对照，验证体系自身已经产出 26 条已修引擎级缺陷（E-1..E-26）、19 条平台/环境缺陷（N-1..N-19）、18 条测试侧缺陷（T-1..T-18）的完整档案，这个项目的真正稀缺资产是**验证方法与失败叙事**，而非功能密度。

| 维度 | 状态 | 关键证据 |
|---|---|---|
| C API 兼容 | ✅ PASS | 官方 c_test.c 直连 16 phase；api_extra/c_api 扩展 |
| 磁盘格式互操作 | ✅ PASS | 黄金比对 9 负载 / 33 文件逐字节一致（rc=0） |
| 磁盘格式**逐字节**等价 | ⚠️ 需收窄 | Snappy 压缩流不保证同字节（§3.3 F 组、§4.2） |
| 单线程行为兼容 | ✅ PASS | 146 用例 × 双后端 |
| 并发行为兼容 | ✅ PASS（本轮新增验证） | db.MultiThreaded oracle 用例；并发初始化缺陷见 §3.3 |

## 2. 优点（附证据）

1. **兼容主张是可证伪的、且已被证伪过多次**。官方源码作为格式权威与测试来源
   在库内固定 commit；黄金比对用"官方写的目录给我们读、我们写的给官方读"
   双向夹逼，每轮修复都附"逐字节 diff 为空"的字节中性证明。
2. **字节中性纪律**。E-14..E-25 每一轮修复后都重跑黄金链并证明 `results.tsv`
   逐字节不变（doc/04 第 838 行起有实例）——这在移植项目里极罕见。
3. **验证装置自身被当作产品对待**。N-1..N-19 十四条全是"装置缺陷冒充结论"的
   档案（logger 不关、POSIX 判据错、submodule 漂移、TMP 伪装、命名空间串档），
   每条都配了负向对照。这使得"Windows 已验证"这类结论第一次具有可复现性。
4. **C 化的架构决策有文档化理由**。值语义 Status、vtable、引用计数、arena
   对齐、pos 游标日志模型——每一处 C++ 惯用法丢失都记着"为什么这样写"（doc/01/02/04）。
5. **三平台 Env 实现（win/posix/memenv）字节对齐**。memenv 做到 rename(2)
   语义的完整等价（E-25 把"自改名释放后继续用"的 SIGSEGV 修掉）是亮点。
6. **文档密度与可追溯性**：doc/01..09 共 9 篇，缺陷从现象→定位→根因→修复→验证
   成链；本轮新增 E-26/T-17/T-18 沿用同一体例。

## 3. 缺点与缺陷清单（本轮独立复核确认的现存项）

### 3.1 Critical

| # | 位置 | 问题 | 影响 | 官方做法 |
|---|---|---|---|---|
| C-1 | `src/skiplist.c`（max_height/next[]）；无锁入口 `src/db.c:1239` | 锁外 Get/迭代对 memtable 的无锁读没有任何 acquire/release 发布协议 | C 层数据竞争/UB；读者可能看到未发布节点；x86 难复现，弱内存序架构不保证 | max_height_ 为 atomic relaxed，next_ 为 atomic 指针，插入 release store / 读取 acquire load |

复现建议：线程 A 持续写不同 key（迫使 memtable 频繁切换），线程 B..D 并发 Get
+ 迭代；TSan 运行应直接报 race；或 ARM64 上高频重复观察漏键/断言。

### 3.2 Major

| # | 位置 | 问题 | 与官方的分歧 |

### 3.3 磁盘格式层审计（第三路 agent，7 条明确 bug + 9 条分歧）

**结论修正**：格式互操作的主体成立（19 项逐条确认一致：block 前缀压缩/重启点、
5 字节 trailer、footer 48 字节、index 缩短键、metaindex/filter 键名、2KiB
filter 分组、bloom 参数、internal filter 策略、WAL writer 分片、WriteBatch 头、
内部键与比较器、coding、CRC 语义、LRU 协议、Snappy 解码器有界检查），
但**不能宣称"逐字节兼容"**——Snappy 压缩流与官方输出不保证逐字节相同，
且存在 7 条明确 bug：

| # | 位置 | 问题 | 级别 |
|---|---|---|---|
| F-1 | `src/filter_block.c:127` | 损坏的 filter offset（`limit < start`）返回空 slice → bloom 判"不存在" → **实际存在的 key 被跳过（假阴性）**。官方对非法区间返回"可能匹配"（保守 true） | 高（读路径数据可见性） |
| F-2 | `src/write_batch.c:182` | `count==0` 提前返回 OK：既不校验 12B 头后的残留 payload，也把 `*last_seq` 写成 `sequence-1`（sequence=0 时下溢）。官方以 `found != Count` 判 corruption。损坏 WAL 可借此传播异常最大 sequence | 高（恢复正确性） |
| F-3 | `src/util.c:438` | CRC32C 查找表用普通全局 `ready` 标志惰性初始化 → 并发首次调用存在 C 数据竞争（官方是函数局部静态初始化的常量表，天然线程安全） | 高（UB/表半初始化） |
| F-4 | `src/cache.c:278` | LRU `NewId` 用无锁全局自增：并发可能产生重复 cache ID → 同一 block cache 内不同表在相同 offset 上键碰撞 → 返回另一张表的 block | 高（返回错数据） |
| F-5 | `src/log.c:295` | **本轮 E-26 补丁自身引入**：BAD/EOF 路径 `fragment` 未初始化却被用于计算物理偏移（官方默认构造空 slice）——已当日修复，可作为"补丁也要被审计"的实例 | 中（已修） |
| F-6 | `src/util.c:694,719` | 超大 bloom（>4Gi bit）位运算截断为 uint32，乘法可溢出为零 → 错误过滤/除零（官方全程 size_t） | 中 |
| F-7 | `src/block.c:115` | 解压长度 0 时把 `malloc(0)==NULL` 误判 OOM（官方 `new char[0]` 不为 null） | 低 |

值得记录的分歧（不修、登记）：Snappy 输出不保证与官方同字节（双方均可解压，
但压缩表文件不逐字节相同——这正是 doc/07 §6 声明的"未证明"被收窄为"已证否"）；
snappy 不拒绝 >UINT32_MAX 输入；filter reader 额外拒绝 `base_lg>30`；
varint64 对非规范 10 字节终止值比官方严格（官方截断、本仓判 bad handle）；
内部键编码入口缺官方的前置断言（seq/type 越界可静默生成）；ReadBlock 一律
按 heap-owned 处理（当前内置 Env 等价）；F-4 的 ID 协议与官方"每实例成员 +
mutex"不等价。**另记一条元教训：审计 agent 在同一天抓到了评估者自己刚提交的
补丁回归（F-5）——新代码必须同样经过独立审计。**

## 4. 不能宣称什么（验证盲区，诚实边界）

1. **弱内存序架构**：skiplist 发布协议缺失（3.1 C-1），x86/Windows 全绿不构成
   ARM 证据。
2. **Snappy 压缩块字节等价**：不仅"未证明"，本轮格式层审计已**证否**——本仓
   Snappy 是独立简化实现，输出不保证与官方 `RawCompress` 同字节（双方均可互解压，
   但压缩 SSTable 文件不逐字节相同）；参考库在本机无 libsnappy 时静默降级为不压缩，
   黄金比对因此全在 no_compression 下做；sanitizer 只证明解码不越界。
3. **泄漏维度仅 Linux 闭环**：Windows ASan 不带 LSan。
4. **跨后端通路未过 sanitizer**：run_cross_backend 两支都是无插桩构建。
5. **故障注入与局部损坏恢复**：corruption_test 12 例、fault_injection 2 例未
   移植；repair 的五处分歧（M-2..M-6）正落在这个盲区。
6. **官方 gtest 套件未直接跑在 kvdb 上**：官方测试是 C++ API 层，无法直连；
   本项目的替代路径是"官方 c_test.c 直连 + 官方 golden 目录 foreign bytes +
   按官方断言逐条移植"，这是方法上的替代而非等价。

## 7. 一句话结论

> 以"兼容"为核心目标的评价维度上，kvdb 已经拿到硬证据（C API 与磁盘格式双向
> 验证、跨五工具链、字节中性纪律）；以"健壮"为核心目标的剩余战场非常清晰：
> **一个内存序缺陷（skiplist 发布协议）、一组 repair 边界语义分歧、一片
> 故障注入/损坏恢复的测试空白**。方法论（doc/11）已经能稳定地把这些空白
> 变成用例再变成缺陷档案——剩下的只是按路线执行。
