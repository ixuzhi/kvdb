# 11 — 检查、检测与评价方法论

本文是 kvdb 兼容实现的**统一评价手册**：有哪些检查层、每层跑什么、证明什么、
不证明什么，以及本轮（2026-09-25 独立复核）新增的三族手段。过程叙事在
doc/04（缺陷档案）、doc/07/08/09（三轮环境验证记录），综合评价在 doc/10。

---

## 0. 总览：五层检查 + 三条横切原则

```text
                    ┌─────────────────────────────────────────┐
   结论可信度 ←    │ L4 静态审计与逐函数对照（人工+agent）      │
                    │ L3 内存安全：ASan / UBSan / LSan          │
                    │ L2 跨后端落盘比对：env_win ⇄ env_posix    │
                    │ L1 跨引擎黄金比对：官方 leveldb ⇄ kvdb    │
                    │ L0 内建回归：移植套件 + 官方 c_test.c 原件 │
                    └─────────────────────────────────────────┘
   横切原则：① 负向对照  ② 装置自身可信  ③ 结论必须带环境坐标
```

每一层的存在理由是**上一层的绿色不蕴含下一层的结论**：

- 套件全绿 ≠ 磁盘格式兼容（可能是两个实现犯同样的错，或从未与官方数据交互）；
- 格式兼容 ≠ 内存安全（arena 未对齐、句柄泄漏、UB 在 x86 上全隐形，doc/07 §6）；
- Windows 绿 ≠ POSIX 绿（POSIX 判据、三元组、命名空间隔离曾各咬一次，doc/09）；
- 文档写着"已验证" ≠ 当前树仍然如此（本轮 E-26：doc/06 P2-4 说 initial_offset
  "只过了代码审查"，树里的 bug 就一直活着，直到用例跟上——**以树为准，文档会过期**）。

## 0.5 一键入口与"多环境怎么选"（2026-09-25 新增）

一台机器上并存多套编译/运行环境（w64devkit、MSYS2 msys/MINGW64/CLANG64、
独立 Cygwin、原生 Linux）时，**不要再靠记忆决定跑哪一套**——两条命令取代
猜测：

```bash
make doctor     # = bash scripts/kvdb_doctor.sh：打印环境矩阵
make check      # = bash scripts/check_all.sh：按矩阵自动跑所有可跑的腿
```

> 支持状态、环境清单与安装命令的**权威页**是
> [doc/12-环境支持矩阵](12-环境支持矩阵.md)；本节只讲入口与判定规则的用法。

| 目标 | 命令 |
|---|---|
| 看本机有哪些环境、各自能跑什么、缺什么怎么装 | `make doctor`（或 `bash scripts/kvdb_doctor.sh`） |
| 一键全检（unit 矩阵 + official + golden + interop + cross-backend + sanitize） | `make check`（证据留档在 `build/checks/<时间戳>/`） |
| 只跑本工具链的移植套件 | `make test` |
| 只跑全部可用环境的 unit 腿（每环境一棵对象树） | `make matrix` |
| 单腿直跑 | `make golden` / `make interop` / `make cross-backend` / `make sanitize` |
| 快速子集 | `bash scripts/check_all.sh --quick`（unit+golden+interop） |
| 只看计划不执行 | `bash scripts/check_all.sh --dry-run` |

判定规则是**腿 → 环境的硬性要求**（doctor 会原样打印）：

- unit：任意编译器；每套环境一棵专用对象树（`build_mingw` / `build_msys` /
  `build_cygwin` / `build_clang64` / `build_linux`…），矩阵一次跑完；
- official/golden/interop：必须 **POSIX g++**（msys / Cygwin / Linux 任一），
  官方库不能在 mingw 目标下构建（N-7）；还需要 `git`；
- cross-backend：需要"一 Windows 目标 + 一 POSIX 目标"各一，脚本在两个命名
  空间里各建临时树；
- sanitize：必须**自带 sanitizer 运行时**的编译器——Windows 上只有 CLANG64
  （gcc 支系实测全部 `cannot find -lasan`），Linux/macOS 的 gcc/clang 都行，
  Linux 还额外获得 LeakSanitizer。

缺环境不是失败而是 **SKIP 行 + 具体安装命令**（`pacman -S …` /
`setup-x86_64.exe -q -P …` / `apt-get install …`），汇总表 rc 只计 FAIL。
命名空间纪律仍由 Makefile 的 `.target` 守卫兜底：混用直接报错，而不是产出
"像链接错误的坏东西"（N-15）。新增目标一律从 Git Bash / MSYS2 / Cygwin /
Linux 调用（需要 `bash`；w64devkit 裸 shell 没有 bash）。

## 1. L0 内建回归（分钟级，每次改代码必跑）

```bash
# Windows 原生（仓库自带 w64devkit）
export PATH="/g/code/kvdb/_tools/w64devkit/w64devkit/bin:$PATH"
make && ./build/kvdb_tests            # 2026-09-25：146 用例

# POSIX（MSYS2；同一份源码的 env_posix 后端）
/d/msys64/usr/bin/bash.exe -lc 'cd /g/code/kvdb && make clean && make && ./build/kvdb_tests'
```

证明什么：移植套件（util/cache/log/batch/skiplist/table/db/c_api + 本轮扩充的
api_extra/format_extra/recovery_extra）全绿；两条后端行为对齐。
**切换工具链前必须 `make clean`**——Makefile 里有三元组守卫会拒绝混用，
这本身是 L4 原则②的产物。

官方用例直连（原件不改一行）：

```bash
# 用官方 leveldb/db/c_test.c 直接链接本仓 libleveldb.a（16 个 phase）
# 已固化进 scripts/run_sanitizers.sh 第 3 步与 run_interop.sh
```

证明什么：C API 层面与官方 C 绑定逐语义一致（这是"接口兼容"主张的直接证据，
而不是"我们自己的测试通过"）。

局限：移植用例只覆盖"我们挑的"场景（覆盖缺口清单见 doc/10 §4）。

## 2. L1 跨引擎黄金比对（核心兼容证据）

```bash
bash scripts/build_official.sh        # 用 MSYS2/Cygwin/Linux 的 g++ 构建官方库（按三元组缓存）
bash scripts/run_golden.sh            # 官方写 → kvdb 读；kvdb 写 → 官方读；双引擎同种子输出逐字节 diff
```

机制（scripts/run_interop.sh、tests/interop/golden_driver.c）：

1. **黄金目录**：官方引擎按 10 种确定性负载（wal / sst / sst-bloom / sst-bigblock /
   edge / tomb / mixed / overwrite …）写出真实目录；
2. **foreign bytes 读取**：kvdb 逐键读官方目录，对每个 SST 走真实的块解析、
   bloom、解压、迭代路径（`OFFICIAL_DBS=` 传给 sanitizer 脚本时同一路径进插桩构建）；
3. **反向**：kvdb 按同一负载写目录，官方引擎读；
4. **逐字节**：同种子下两个引擎各自产出的 MANIFEST/CURRENT/*.log/*.ldb
   与摘要 `results.tsv` 逐字节 diff（当前 33 文件、9 负载、109 项 PASS）。

证明什么：磁盘格式兼容不是"我们同意的"，是"官方写的我们读得对、我们写的官方认"。

局限（doc/07 §6）：参考库在无 libsnappy 环境下把 kSnappyCompression 静默降级为
不压缩，**压缩块的字节级等价尚未证明**；黄金比对是逐字节相等，任何"合法但不同"
的编码差异都会误报——这不是缺陷而是该方法的敏感度来源。

## 3. L2 跨后端落盘比对（同一份源码、两个 Env 实现）

```bash
bash scripts/run_cross_backend.sh
```

第一次把 `env_win.c` 与 `env_posix.c` 的落盘字节放在一起比对：9/9 模式、
33 文件 SAME、58 PASS、0 FAIL；含 8 进程并发争用 `LOCK` 的多进程互斥段
（闭环 doc/06 P2-6）。

证明什么：平台抽象没有渗漏——Win32 与 POSIX 写出的字节必须相同，锁语义必须等价。

## 4. L3 内存安全（ASan / UBSan / LSan）

```bash
# Windows 主机：只有 MSYS2 CLANG64 链带 sanitizer 运行时
# （gcc 支系实测全部 cannot find -lasan，doc/07 §1）
/d/msys64/usr/bin/bash.exe -lc 'cd /g/code/kvdb && MSYSTEM=CLANG64 bash scripts/run_sanitizers.sh'

# 原生 Linux：gcc 自带，且 LSan 默认开
bash scripts/run_sanitizers.sh
```

机制要点：

- `-fno-sanitize-recover=all`：首次 UBSan 报告即终止，**退出码 0 = 零报告**；
  需要"枚举全部问题"时另跑一份可恢复构建（doc/07 §6 第二条）；
- 泄漏维度 2026-09-20 才真正闭环（Linux 首跑 929,842 B / 201 分配，逼出 E-16/17/18
  与 T-12/T-13）；Windows 版 ASan 不带 LSan，这条"做不到"仅对 Windows 成立；
- 脚本的三道守卫本身就是方法论资产：归档时效守卫（src 比归档新 → rc=2）、
  工具链守卫、Windows 三元组配非 clang 直接 exit 2——**都做过负向对照**。

已证明的缺陷类型：misaligned address（P0-8 arena）、句柄永不归还（P0-9 logger）、
nonnull-argument（P0-10，Linux glibc 才判罚）、global-singleton 抑制泄漏可见性
（E-19）、release 后使用（E-25，rc=139）。

## 5. L4 静态审计与逐函数对照

### 5.1 人工对照法

模块与官方文件的映射是一一对应的（doc/01 有全表），因此审计可以按文件推进：
`db.c↔db_impl.cc`、`version_set.c↔version_set.cc`、`skiplist.c↔skiplist.h`、
`log.c↔log_reader.cc/log_writer.cc`、`block/table/filter_block↔table/`、
`repair.c↔repair.cc`、`db_iter.c↔db_iter.cc`、`iterator.c↔merger.cc`。

**审计纪律**：

1. 以工作区当前树为准，文档结论需复核（本轮 E-26 即例）；
2. finding 分级：critical=可致数据损坏/崩溃且在正常路径上；major=与官方行为
   分歧且可致数据丢失/修复失败；minor=公开选项语义失效但不产生错误数据；
3. 每条 finding 必须给复现步骤，不接受"读着像有问题"。

### 5.2 C 语言使用检查（静态 + UBSan 混合腿）

严格告警矩阵（GCC `-Wall -Wextra` 6 条 + clang 额外类别 + `-fanalyzer` +
UBSan nonnull 判定）曾一次逼出六条引擎缺陷（E-19..E-23、E-25）与三条测试侧
缺陷（T-14..T-16）。要点：**编译器差异本身是探测器**（clang 的
`-Wignored-qualifiers`/`-Wstring-concatenation`、glibc 的 nonnull 属性，
都在 GCC 侧完全隐形）。

### 5.3 独立复核 agent（2026-09-25 新增）

用三个并行只读审计 agent 复核既有文档的结论，分工：db 生命周期层、测试套件质量、
磁盘格式层。价值不在"发现全新 bug"（多数命中已归档条目），而在：

- **证伪能力**：agent 确认 writer 队列协议、version 引用计数、log_and_apply
  提交顺序、压缩挑选、obsolete 回收等 12 个关键点与官方一致；
- **文档漂移检测**：E-26 正是被"以树为准"的指令逼出来的；
- **零修改**：审计全程只读，不污染被审对象。

## 6. 本轮（2026-09-25）新增的三族检测手段

| 族 | 用例/脚本 | 锚定的缺陷或盲区 |
|---|---|---|
| 参数化边界矩阵 | `log.ReadStart` … `log.ReadPastEnd`（14 例，官方 `log_test` 的 initial-offset 家族原样移植，含分片记录跨 4 块、块尾 trailer、padding 起点、越界偏移） | E-26（skip 缺失、偏移记错对象、缺 resyncing） |

## 7. 三条横切原则（每条都有本项目实例）

**① 负向对照**：任何"新用例抓到了 bug"或"修复后全绿"的结论，都必须做
"摘掉修复 → 用例恰好失败"的对照，并先确认被对照的二进制真的变了
（doc/07 §4 记录过一次"对照无效"：`ar r` 因更早的失败没有真正替换成员，
拿到的还是旧归档，假绿）。本轮 E-26 的对照结果：摘掉 `skip` 后 14 例中 13 例失败。

**② 装置自身可信**：验证装置的缺陷会冒充结论。N-6..N-19 共十四条全是这一类：
logger 不关导致"重开必失败"的假象、"官方源码被改动"守卫把 submodule 指针漂移
算成改动、POSIX 判据只认 `-cygwin` 而本机报 `-msys`、本地化 shell 里
`grep 'warning:'` 恒为 0、`TMP` 缺失伪装成后端不一致。规则：**每个守卫都要有
自己的负向对照；每个"不一致"先怀疑装置**。

**③ 结论带环境坐标**：任何"已验证"必须写明机器/工具链/三元组/运行时
（doc/09 的五条腿：MSYS2 msys、MINGW64、独立 Cygwin、CLANG64、原生 Linux）。
"Windows 已验证"在另一台 Windows 机器上曾不可复现——因为脚本把主机 OS
当成了编译器目标。

## 9. 补法路线（把"未覆盖"变成"已覆盖"的最小代价排序）

1. **skiplist 发布协议**：给 `next[]`/`max_height` 加 acquire/release（或 C11
   atomic），TSan + ARM64 验证——成本最小、风险最高。
2. **故障注入 Env + corruption_test 移植**：官方 corruption_test 12 例 +
   fault_injection 2 例；需要先实现 SpecialEnv（可控读写失败/损坏注入）。
3. **version_set 选择层用例**：`FindFile` 6 例 + `AddBoundaryInputs` 7 例，
   直接针对压缩输入正确性。
4. **恢复与日志复用**：`reuse_logs`（现恒 false）+ recovery_test 6 例。
5. **真实 Env 契约测试**：官方 env_test 系列（reopen/truncate/锁/权限）。
6. **历史 issue 回归**：issue178/200/320 三例（删除复活、换向迭代、删插交错）。

每项完成后按本手册的格式补：doc/04 记缺陷叙事、doc/06 更新状态、
套件加用例并做负向对照。

补充（2026-09-25 格式层审计后的插队项）：**F-1 filter 假阴性**、**F-2
count=0 batch 校验缺失**、**F-3 CRC 表初始化竞争**、**F-4 cache NewId 竞争**
四条应排在 repair 对齐之前——它们各自的修复都在个位数行数级，且都位于
"正常输入永绿、边界条件致命"的位置。
