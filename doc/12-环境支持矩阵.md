# 12 — 环境支持矩阵（当前支持状态的唯一权威页）

本文回答三个问题：**kvdb 支持哪些编译/执行环境、每套环境能承担哪些验证、缺环境
怎么装**。它是"现在"的单页权威；doc/07 / 08 / 09 是各轮验证的历史记录（细节与
失败叙事留在那里），doc/11 是方法论，本文只做支持状态与操作手册。

> **机器可读的真源**：`make doctor`（= [scripts/kvdb_doctor.sh](../scripts/kvdb_doctor.sh)）
> 现场探测本机环境并打印同一张矩阵。文档可能过期，doctor 不会——两者不一致时
> 以 doctor 输出为准，并回来修本文。

## 1. 支持的环境清单

| 环境 | 获取方式 | 目标三元组 | Env 后端 | sanitizer | 专用对象树 | 官方库可构建 | 能承担的腿 |
|---|---|---|---|---|---|---|---|
| **w64devkit**（仓库自带） | `_tools/w64devkit/`，首次构建自动下载；或 GitHub Release 手动放置 | `x86_64-w64-mingw32` | `env_win` | ✗ | `build_mingw` | ✗（mingw 目标不行，见 N-7） | unit、官方 c_test、cross-backend 的 Windows 半边 |
| **MSYS2 msys** | `pacman -S --needed make gcc git` | `x86_64-pc-msys` | `env_posix` | ✗ | `build_msys` | ✓ | unit、official、golden、interop、cross-backend 的 POSIX 半边 |
| **MSYS2 MINGW64** | `pacman -S --needed mingw-w64-x86_64-gcc` | `x86_64-w64-mingw32` | `env_win` | ✗ | `build_mingw64` | ✗ | 同 w64devkit（unit、c_test、cross-backend Win 半边） |
| **MSYS2 CLANG64** | `pacman -S --needed mingw-w64-x86_64-clang` | `x86_64-w64-windows-gnu` | `env_win` | **✓（Windows 上唯一）** | `build_clang64` | ✗ | 全部 + **sanitize**（ASan+UBSan；无 LSan） |
| **独立 Cygwin** | `setup-x86_64.exe -q -P gcc-core,gcc-g++,make,git` | `x86_64-pc-cygwin` | `env_posix` | ✗ | `build_cygwin` | ✓ | 同 msys（unit、official、golden、interop） |
| **原生 Linux** | `apt-get install -y build-essential git cmake`（Debian/Ubuntu 系） | `x86_64-linux-gnu` | `env_posix` | **✓（gcc 自带，另得 LSan）** | `build_linux` | ✓ | **全部**（含 sanitizer+LSan，是覆盖面最广的一套） |

关于 sanitizer 的硬事实（doc/07 §1、doc/09 §4.3 实测）：Windows 上三支 gcc
（w64devkit 16.2、MSYS2 13.3、独立 Cygwin 14.4）`-fsanitize=address,undefined`
一律 `cannot find -lasan/-lubsan`；只有 CLANG64 随包交付
`libclang_rt.asan_dynamic-x86_64.dll`。Linux 的 gcc 12 自带 libasan/libubsan/
libtsan，libasan 还带 LeakSanitizer。

## 2. 安装组合手册（命令级）

### 2.0 宿主工具要求

| 工具 | 谁需要 | 说明 |
|---|---|---|
| C11 编译器 | 全部 | gcc 或 clang 均可；w64devkit 自带 gcc 16.2 |
| `make` | 全部 | w64devkit / MSYS2 / Cygwin / Linux 均自带 |
| `bash` | **所有 `scripts/*.sh`** | w64devkit **只有 busybox sh、没有 bash**：纯 w64devkit 环境能跑 `make`/`make test`，但跑不了 `make check`。Windows 上请配 Git Bash / MSYS2 / Cygwin 任一提供 bash |
| `git` | official / golden / interop | 构建官方库前会校验 pin commit |
| `g++` | official / golden / interop | 官方 leveldb 是 C++；**mingw 目标编不了**（N-7），须 POSIX g++ |
| `sed`/`awk`/`find`/`tee` | 脚本 | 任何 POSIX 基础系统皆可（busybox 也够） |

doctor 对 MSYS2 安装位置按 `MSYS2_ROOT` → `/d/msys64` → `/c/msys64` →
`/opt/msys64` → PATH 的顺序探测；Cygwin 探测 `/c/cygwin64`、`/c/cygwin` 与
任意 `*cygwin*` 三元组的 `/usr/bin/gcc`。装在非常见位置时：MSYS2 设
`MSYS2_ROOT`；Cygwin 直接在其终端里跑 doctor（走 PATH 回退）。

### 2.1 组合 A — Windows 最小可用（unit + 官方 c_test）

需要：**w64devkit**（Windows 目标编译器）+ **Git Bash**（提供 bash）。

```bash
# 1) 取 w64devkit（二选一）
#    a. 下载 https://github.com/skeeto/w64devkit/releases 的 w64devkit.exe
#       （自解压 7z），在本仓库运行它；或已有 w64devkit.7z 时：7z x w64devkit.7z
#    b. 直接下载发行 zip/7z 并解压
# 2) 放到期望布局（doctor 按此路径识别）
mv w64devkit _tools/w64devkit          # → _tools/w64devkit/w64devkit/bin/gcc.exe
# 3) 验证
_tools/w64devkit/w64devkit/bin/gcc.exe -dumpmachine   # 期望 x86_64-w64-mingw32
```

> 诚实备注：根 README 写“首次构建时自动下载”，但 Makefile 里没有下载逻辑——
> 实际是**放好即用**；`make` 不会替你抓 w64devkit。
> 不落 `_tools` 也行：把解压目录的 `bin` 放进 PATH，doctor 会把 PATH 上的
> mingw gcc 认作 w64devkit 行。

```bash
# Git Bash（https://git-scm.com/download/win 安装后自带）中：
export PATH="/g/code/kvdb/_tools/w64devkit/w64devkit/bin:$PATH"
make test          # 或 make
bash scripts/kvdb_doctor.sh    # 确认 w64devkit 行 yes
```

能跑：unit、官方 c_test、cross-backend 的 Windows 半边。
**跑不了**：golden/interop（缺 POSIX g++）、sanitize（gcc 无运行时）。

### 2.2 组合 B — Windows 全功能（推荐）

= 组合 A（或改用 MSYS2 MINGW64）+ **MSYS2 msys 层**（g++ → official/golden/
interop）+ **MSYS2 CLANG64**（sanitizer）。

```bash
# 1) 装 MSYS2：官网 msys2.org 下载安装器（默认 C:\msys64）或免安装 .sfx.exe
# 2) 打开“MSYS2 MSYS”终端（msys 层），执行：
pacman -Syu                          # 核心更新；按提示关窗重开后再跑一次
pacman -S --needed make gcc git      # msys 层：g++ 官方库 / golden / interop
# 3) 可选：Windows 目标的两层（替代/补充 w64devkit）
pacman -S --needed mingw-w64-x86_64-gcc     # unit + c_test
pacman -S --needed mingw-w64-x86_64-clang   # Windows 上唯一的 sanitizer 源
# 4) 验证与全检（Git Bash 里）
bash scripts/kvdb_doctor.sh          # 期望 w64devkit / msys2-msys / msys2-clang64 = yes
make check
```

MSYSTEM 层的两种用法：

```bash
# 从 Git Bash 调 msys 层（check_all 内部就是这么路由的）
/d/msys64/usr/bin/bash.exe -lc 'cd /g/code/kvdb && ./build/kvdb_tests'
# 直开对应终端：“MSYS2 CLANG64”终端里跑 sanitizer 腿
MSYSTEM=CLANG64 /d/msys64/usr/bin/bash.exe -lc 'cd /g/code/kvdb && bash scripts/run_sanitizers.sh'
```

### 2.3 组合 C — 追加独立 Cygwin（第五命名空间）

```bash
# 静默安装（图形安装则勾选同名包）
setup-x86_64.exe -q -s https://mirrors.kernel.org/sourceware/cygwin/ \
  -P gcc-core,gcc-g++,make,git,binutils
# 完成后在 Cygwin 终端：仓库位于 /cygdrive/c/code/kvdb（或你的盘符）
cygpath -u 'C:\code\kvdb'            # → /cygdrive/c/code/kvdb
bash scripts/kvdb_doctor.sh          # cygwin 行应 yes
```

纪律：与 msys 的运行时互不可见，**对象树与官方库归档都不可跨用**（N-14/N-15）。

### 2.4 组合 D — Windows + WSL（想在本机拿到 LSan 全覆盖）

```powershell
wsl --install -d Ubuntu        # 管理员；会下载发行版（需联网）
```

```bash
# WSL 内（Ubuntu）
sudo apt-get update && sudo apt-get install -y build-essential git cmake
cd /mnt/g/code/kvdb            # 仓库在 Windows 盘时走 /mnt/<盘符>
bash scripts/kvdb_doctor.sh    # linux 行应 yes，SAN=yes（gcc 自带 LSan）
bash scripts/check_all.sh      # 全链；覆盖面最广的一套
```

> 本机 2026-09-25 时尚未安装任何 WSL 发行版，此路线**未在本机验证**；预期基线
> 见 doc/08（原生 Debian 12 / gcc 12.2 三轮全通路通过）。

### 2.5 组合 E — 原生 Linux（最简，一套 gcc 全包）

```bash
# Debian / Ubuntu
sudo apt-get install -y build-essential git cmake
# Fedora / RHEL
sudo dnf install -y gcc gcc-c++ make git cmake
# Arch
sudo pacman -S --needed base-devel git cmake

cd /path/to/kvdb && bash scripts/check_all.sh
```

### 2.6 离线 / 内网与特殊路径

```bash
# MSYS2 离线：联网机预下载，再拷 /var/cache/pacman/pkg/*.zst 到离线机
pacman -Sw --needed make gcc git mingw-w64-x86_64-clang
pacman -U /path/to/*.zst
# Cygwin 离线：setup-x86_64.exe -q -D -L <本地包目录> -P gcc-core,gcc-g++,make,git
# w64devkit 本身就是单文件 7z，拷贝即用
```

- MSYS2 装在非常见位置：`export MSYS2_ROOT=/你的路径` 后再跑 doctor/检查。
- 受管机器/杀毒软件：把仓库目录与 `_tools` 加入排除项——w64devkit 每次调用都
  要扫 gcc/cc1/as 的 exe，实时防护下全量构建会从秒级变成分钟级。

### 2.7 按目标选组合（速查）

| 目标 | 最小组合 | 命令 |
|---|---|---|
| 只跑移植套件 | w64devkit（或 mingw64）+ Git Bash | `make test` |
| 全部格式/兼容证据 | + MSYS2 msys 或 Cygwin | `make check` |
| 内存安全（Windows） | + MSYS2 CLANG64 | `make sanitize` |
| 内存安全 + 泄漏（最全） | Linux 或 WSL 上一套 gcc | `make check`（含 LSan） |
| 五命名空间全矩阵 | A/B/C/D 全装 | `make doctor && make check` |

安装后自检清单：① `bash scripts/kvdb_doctor.sh` 各行符合预期 → ② `make test`
单树绿 → ③ `make matrix` 全在场环境绿 → ④ `make check` 全链 rc=0（证据在
`build/checks/<时间戳>/`）。

## 3. 腿 → 环境要求（判定规则）

| 腿 | 硬性要求 | 说明 |
|---|---|---|
| unit（移植套件） | 任意 gcc/clang | 每套环境一棵专用对象树；`make matrix` 一次跑完所有在场环境 |
| official（构建官方 leveldb） | POSIX g++ + git | 官方库不能在 mingw 目标下编译（N-7）；归档按三元组缓存于 `build/interop/official/<triple>/` |
| golden（逐字节黄金比对） | 官方库就绪 + POSIX 壳 | 三向摘要：official→kvdb、kvdb→official、同种子逐字节 diff |
| interop（互操作 + 官方 c_test） | 同 golden，另需 `git`；`RUN_C_TEST=1` 才跑未修改的官方 `c_test.c` | |
| cross-backend（双后端字节互比 + 8 进程锁竞争） | 一 Windows 目标 + 一 POSIX 目标各一 | 必须在 POSIX 壳里运行并显式传 `CC_WIN`；`TMP` 需为 Win32 形状（`cygpath -w /tmp`） |
| sanitize | **自带 sanitizer 运行时**的编译器 | Windows 仅 CLANG64；Linux/macOS 的 gcc/clang 均可；Linux 默认开 LSan（`SAN_DETECT_LEAKS=0` 关） |

**最短 PASS 路径**：
- Windows：w64devkit（或 mingw64）拿 unit+c_test + msys（或 Cygwin）拿
  golden+interop；想要内存安全再加 CLANG64。
- Linux：一套 gcc 全包（含 LSan）。

## 4. 一键入口

```bash
make doctor     # 环境矩阵（现场探测；缺环境附安装命令）
make check      # 一键全检：按矩阵自动路由，证据留档 build/checks/<时间戳>/
make matrix     # 只跑全部在场环境的 unit 腿
make test       # 只跑当前工具链的移植套件
```

单腿直跑：`make golden` / `make interop` / `make cross-backend` /
`make sanitize`；子集与预案：`bash scripts/check_all.sh --quick`、
`--legs=unit,golden`、`--dry-run`（只打印计划）。

**SKIP 语义**：缺环境不是失败——check_all 记 SKIP 行并附安装命令，退出码只计
FAIL。汇总口径见每次运行目录里的 `summary.txt`。

## 6. 共存纪律（每条都有血的教训）

1. **每套命名空间在它自己的 shell 里跑**。msys-2.0.dll 与 cygwin-1.dll 互不可见，
   跨命名空间拿归档会得到"像链接错误"的假象（N-7、N-14、N-15）。check_all 按
   探测到的 shell 逐腿路由，正是这条纪律的自动化。
2. **对象树按环境分开**（`build_mingw` / `build_msys` / `build_cygwin` /
   `build_clang64` / `build_linux`…）。Makefile 的 `.target` 守卫记录树的归属
   三元组，混用直接报错并指名 `make clean`，而不是产出坏东西（N-15）。
3. **默认树 `build/` 归 POSIX 腿所有**。golden/interop 在 POSIX 壳里链接
   `build/libleveldb.a`，所以 `make check` 会先在 POSIX 壳里重建默认树
   （`kvdb-lib` 腿）；Windows 的 unit 腿各用各的专用树，互不干扰。
4. **官方库归档按三元组缓存**（`build/interop/official/<triple>/`）：msys 与
   Cygwin 运行时互不可见，串档会得到"官方源码被改动"式的假象（N-14）。
5. **TMP 必须是对端形状**：原生 Windows 编译器不能拿 MSYS 形状的 `/tmp`
   （N-13）；cross-backend 腿由编排器显式传 `TMP=$(cygpath -w /tmp)`。
6. **环境层不进全局变量**。编排器曾把 `MSYSTEM=CLANG64` 留在全局泄漏到后续腿，
   导致 w64devkit gcc 的 `.s` 被 clang64 里 LLVM 版 `as` 汇编、报 `.ident`
   未知指令——单腿验证永远看不到，只有全链顺序才显形（N-20）。现在
   `MSYSTEM` 是每次调用的显式参数。

## 7. 故障速查（症状 → 原因 → 出处）

| 症状 | 原因 | 出处 |
|---|---|---|
| `unknown directive .ident`，只在全链跑时出现 | `MSYSTEM=CLANG64` 泄漏，`/clang64/bin/as` 是 LLVM 汇编器 | N-20 |
| `cannot find -lasan` / `-lubsan`（Windows） | 所用 gcc 无 sanitizer 运行时；换 CLANG64 | doc/07 §1 |
| `detect_leaks is not supported` | Windows 版 ASan 不带 LSan；泄漏维度只能在 Linux 闭环 | doc/07 §6 |
| 归档/对象树"串档"、`Nothing to be done` 却拿着别人的二进制 | 跨命名空间复用；按三元组分树分缓存 | N-14、N-15 |
| 官方库构建被拒 | 用了 mingw 目标；官方库需 POSIX g++ | N-7 |
| "官方源码被改动"守卫误报 | 嵌套 submodule 指针漂移被算成改动 | N-9 |
| `TMP` 相关失败伪装成后端不一致 | 跑腿前缺 TMP 守卫 | N-13 |
| `build/ holds objects built for …` | 换工具链未 `make clean` | Makefile `.target` 守卫 |

  新的命名空间或分层纪律，在 §6 追加一条并同步 doc/11 §0.5。
- 每轮验证的历史细节（装了什么、卸了什么、逐条读数）不写进本文，回填到
  doc/07/08/09 对应轮次；本文只保留"当前支持什么、怎么用、缺了怎么装"。
- 本文任何"支持/不支持"的断言都应能指向一次实跑记录（证据目录或文档轮次），
  推论要显式标注为推论（本项目的老规矩，见 doc/07 §7）。
