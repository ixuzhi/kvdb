# 13 — 正交验证：方法设计、步骤、自验证与对比验证

本文是 2026-09-25 建立的**独立验证体系**的完整文档：为什么做、怎么设计、
从零怎么跑、过程中撞到并解决了什么、方法本身如何被验证（自验证）、如何与
官方引擎同种子对跑（对比验证），以及**明确没有验证到的部分与 TODO**。
总入口：`bash tools/verify/verify_all.sh [quick|full]`（= `make verify`），
自验证入口：`bash tools/verify/verify_mutants.sh`。证据留档 `build/verify/<时间戳>/`，
退出码 = 失败腿数。

---

## 1. 为什么要正交验证

既有体系（doc/11 五层）已经很强，但每一层的"绿色"都有方向性：

| 既有证据 | 它证明什么 | 它的盲区 |
|---|---|---|
| 移植套件 146 例 | 与官方断言逐条一致 | 断言本身的错位会被忠实继承；只测"被想到的"场景 |
| 黄金比对（字节） | 与官方落盘逐字节一致 | 写入侧共谋时不可察（两个实现犯同样的错）；受官方夹具限制 |
| 官方 c_test 直连 | C API 语义一致 | 官方没断言的（快照中途、崩溃瞬间、损坏字节）无人问津 |

正交验证补的是**与移植断言无关**、**与官方字节无关**的证据：预言机是自建的，
判定是物理事实（不崩溃、已确认的前缀、快照时刻的模型），参照系是第三种语言
的独立实现。体系的第一性原理：**每个绿色结论都要能回答"如果这里错了，谁会
先发现"**。

## 2. 架构设计

### 2.1 四条设计原则

1. **预言机独立**：任何判定不引用 leveldb 的断言或实现；模型自己写、哈希
   自己实现、CRC 自己实现。
2. **方向正交**：五腿（+ 一条官方 oracle 段）分别沿互不重叠的维度切入——状态空间（模型差分）、
   字节空间（格式探针）、时间轴（快照/崩溃）、破坏轴（损坏）、实现轴（官方
   对照）。
3. **只经公开面**：B/F/D/C 四腿只使用 `include/leveldb/c.h`；不触碰内部
   符号，顺带成为 C API 面的黑盒回归。
4. **装置可被审计**：每条检查都要能证明"它坏了会报"（§5 变异检测）、"它不是
   空转"（负向对照）、"它没看错"（§4 由官方实现仲裁）。这是本体系与普通
   "多写点测试"的分水岭。

### 2.2 五腿结构（+ B2 bloom oracle 段）

| 腿 | 输入 | 独立预言机 | 判定 | 失败含义 |
|---|---|---|---|---|
| **A** model_fuzz | 公开 C API | 自建排序数组模型（二进制键） | 每次 Get/全量扫描 = 模型 | 读写语义偏离 |
| **B** format_probe | 关闭的 DB 目录 | JS 从零实现的格式解析器（CRC32C/varint/日志/VersionEdit/块/snappy/bloom） | 每块 CRC、index 路由、bloom 成员性、层级不重叠、无孤儿文件；与官方目录摘要比对 | 格式或哈希层偏离 |
| **F** iterator_snapshot | 公开 C API + 单调模型 | barrier 时刻的模型副本 | 正向+反向全量迭代 = 快照 | 快照隔离/可见性泄漏 |
| **D** crash_torture | 公开 C API | fsync 边记的确认日志 | 重开状态 = 确认序列的**前缀** | 崩溃一致性破坏 |
| **C** corrupt_fuzz | 字节变异后的目录 | 无（性质断言） | 只能"干净打开"或"以 Corruption 拒绝"；**不得崩溃/挂死** | 鲁棒性破坏 |

### 2.3 与既有体系的关系

```
                 移植套件    黄金比对    sanitizer    本轮正交段
断言层            ✓           -           -           -（刻意不用）
字节层            -           ✓           -           ✓（独立解析器）
内存安全          -           -           ✓           -
状态/时间/破坏轴   -           -           -           ✓
实现对照          c_test      ✓(双写)     -           ✓(同种子双跑)
装置自审          部分         ✓          ✓           ✓（变异矩阵）
```

## 3. 验证步骤（从零可复现）

### 3.1 前置

```bash
bash scripts/kvdb_doctor.sh                    # 环境矩阵（doc/12）
bash scripts/build_official.sh                 # 官方对照归档（缺则相关腿 SKIP）
```

### 3.2 一键与从零复跑

```bash
bash tools/verify/verify_all.sh                # 一键（quick）
rm -rf build/verify && make clean && bash tools/verify/verify_all.sh full   # 从零 full
```

`verify_all.sh` 会：① 校验 `build/libleveldb.a` 的三元组与当前工具链一致
（不一致或缺失则 `make clean` 重建——官方脚本"混档拒绝"纪律的延续，doc/04
N-14/N-15）；② 编译全部 harness；③ 逐腿执行并把日志/JSON 写入
`build/verify/<时间戳>/`；④ 跑负向对照与对比段；⑤ 打印汇总表。

### 3.3 各腿标准步骤

- **A**：`model_fuzz <seed> 10000 <dir>`——建库→随机批写/批删/Get/全扫描/
  全压缩/周期重开→最终全扫描=模型。二进制键（内嵌 0x00/0xFF、前缀族）保证
  路径多样。
- **B**：`mkfixture_kvdb`（不开 bloom）与 `mkfixture_official`（官方库）各写
  一份 20 键库并压缩；`format_probe.js <dir>` 出 JSON（零 problems 为过）；
  `--compare A B` 逐类给 SAME/DIFF。
- **F**：`iterator_snapshot <seed>`——写线程持锁推进模型，读者在 barrier 取
  模型副本并建迭代器；写线程跑完 4000 次跨 flush 操作后，正向与反向全量迭代
  必须 = 副本。
- **D**：`crash_torture write`（逐条 sync 写 + fsync 记账 → 进程自毁）→
  `verify`（重开，键集合必须是 [0,max] 的前缀且值正确）。`verify-drop K` 是
  负向对照（故意删一个已确认键，必须报 rc=3）。
- **C**：`corrupt_fuzz.js 150`——每轮复制健康夹具、按种子翻 1~8 字节
  （MANIFEST 25% / .ldb 45% / .log 30%），子进程跑 `reopen_probe`（15s
  超时）；退出码 ≥128 或超时 = 失败。

### 3.4 自验证（变异检测）

```bash
bash tools/verify/verify_mutants.sh    # → build/verify/mutants/<ts>/matrix.tsv
```

对每个一次性破坏（bloom 哈希乘法→加法、跳过 WAL 追加、批计数不增、迭代器
快照边界失效），在**丢弃式副本树**里重建引擎与全部 harness，然后问五种方法
各自"报不报"。读法：`caught` = 方法在坏引擎上失败（好），`missed` = 放过
（盲区，需记账）。

### 3.5 对比验证

`verify_all.sh` 的 COMPARATIVE 段：同一批 harness 分别链接官方归档与本仓
归档，**同一批种子**跑：`model_fuzz` / `iterator_snapshot` /
`crash_torture` 在两个引擎上结果都必须为真。附加对比：
`official_table_check`（官方 reader + `verify_checksums=true`）读 kvdb 写出的表。

## 4. 验证中遇到并解决的问题

按归属分三类。**探针/装置侧的错误与引擎缺陷同等重要**——它们是本体系的
可信度成本表。

### 4.1 探针/装置侧（本轮实际踩到并修复）

| # | 现象 | 根因 | 解决 | 发现方式 |
|---|---|---|---|---|
| P1 | MANIFEST 全记录"CRC 失配" | unmask 写成"右旋 15 + delta"，官方是**先减 delta 再左旋 15** | 逐字复刻官方 `crc32c.h`；`official_crc.cc` 调官方 crc32c.cc 仲裁 | manifest 解析全面失败 |
| P2 | 每个 SST 块都"CRC 失配"（连官方写的文件也失配） | 块尾语义整个搞反：官方 `WriteRawBlock` 里**句柄 size 是纯内容长度**，尾为 `[type:1][crc:4]`，CRC 覆盖 `内容‖type` | 重写 `readBlock`；`official_table_check`（官方 reader 校验和开启）+ `official_footer`（官方 Footer 解码）双向仲裁 | 官方能读、只有探针报错 |
| P3 | 空 metaindex 反复误报 | 空块编码是 8 字节 `restart[0]+count`（官方 BlockBuilder 构造即压 restart[0]），空块不进入重启点循环 | 识别 `restartBase==0` 特例 | 官方 `Footer::DecodeFrom` 打脸 |
| P4 | "index 键必须是首键前缀"误报 | index 键是**最短分隔符**语义，不是前缀 | 换成真正的路由不变量：每个键经 index 二分必须落到含它的块 | 官方 writer 源码 |
| P5 | **JS 探针自实现的 bloom 成员性检查在健康引擎上连续误报四次**（filter-block 分块、编码 k、user-key 提取三层耦合，我把它写成了 rocksdb 风格） | 自研预言机的第二类失败模式：不是细节错，而是整个判定层次选错 | **退役该检查**（探针只保留结构性检查），成员性改由**官方 FilterPolicy 做 oracle**（`official_bloom_check.cc`，对 kvdb 写出的 filter 字节提问）；健康表上 20 键 0 假阴性 | 变异矩阵"caught"与健康引擎复跑互相打脸（真检查必须先在健康引擎上零误报） |
| P6 | harness 给 `leveldb_destroy_db` 传 NULL → 段错误（一度像引擎缺陷） | 官方 c.cc 对所有 options 指针**无条件解引用**，NULL 非法 | 修 harness；写进工具注释 | 核对官方 c.cc |
| P7 | compare 报 tables DIFF | 夹具未清：旧 20 键被新序列号覆写，internal key 变了 | 每轮 `rm -rf` 夹具 | 摘要不同但条目数相同 |
| P8 | verify_all 在 msys 壳里四腿全败 | build/ 还是 mingw 归档，msys make 被 `.target` 守卫拒绝（守卫消息不含 "error" 被 grep 吞掉） | 脚本自检三元组并按需 clean 重建 | 链接错误 `_assert` |
| P9 | 官方归档在 mingw 壳里链不上 | 跨命名空间串档（N-14 同款，自找的） | 三元组比对：不匹配记 SKIP 并提示换壳 | g++ 链接失败 |
| P10 | 从零复跑第一步就退出 | 自愈逻辑排在"库存在"检查之后 | 重排顺序 | "missing libleveldb.a" |
| P11 | snap_leak 变异全员漏检 | 该变异对正/反向全量扫描都**近似等价**（旧版本被合并逻辑吞掉）——等价变异陷阱 | 如实归类为等价变异并记账；迭代器快照腿仍补**反向扫描**（对未来的非等价可见性变异有价值） | 变异矩阵 |
| P12 | 变异矩阵首跑输出自相矛盾 | spec 分隔符与 `local a=b=c` 赋值坑 | 换 `#` 分隔、拆开赋值 | 矩阵本身不可信 |
| P13 | `/tmp` 在 Git Bash 与 msys 不是一处；官方 `Read` 签名记错；探针错误无栈 | —— | 夹具进仓内目录、查头文件、错误带栈行 | 各自当场暴露 |
| P14 | **矩阵把"工具不存在"当成 caught**（msys 登录壳丢 node → 四行 probe/oracle 全"caught"） | 判定层没有区分"基础设施故障"与"检出" | 脚本加 node 解析器；夹具未生成/工具缺失一律记 **skip** | 矩阵"抓到了"不可能被抓的 snap_leak |
| P15 | **D 腿的检查器有真实漏洞**：前缀性质允许"空前缀"，"WAL 全丢"变异因此通过；此前矩阵里的 crash_torture"caught"其实是我 NULL 写选项 bug 造成的假阳性 | 性质表述不完整：确认过的写（sync+fsync）必须**全部**在场 | 增完整性断言 `max == ack`；修复后 skip_wal 被如实抓住 | 变异检测（这是"检查器自身漏洞被变异测试发现"的完整案例） |

### 4.2 引擎侧（本轮触及）

- **E-27**：`ldb_hash` 对 `{NULL,0}` 空 slice 做非零偏移指针运算——由新接入
  路由的 clang64 sanitizer 腿抓到（doc/07 体系），已修并入档 doc/04。
- 其余引擎结论均为"与官方一致"或"合法拒绝"，无新缺陷。

### 4.3 方法论沉淀

- "不一致先怀疑装置"再次被验证：P1/P2/P3/P4 全部是探针错，官方实现每次判对。
- **变异矩阵是发现"检查自身漏洞"（P5）的唯一手段**——没有它，bloom 假阴性
  会永远只出现在 JSON 里。
- 独立预言机的价值不在永远正确，而在其错误**可被第三方仲裁**且与被测对象无关。

## 5. 自验证：变异检测矩阵（实测）

矩阵（`verify_mutants.sh`，msys 后端，2026-09-25 17:43 最终版；每格都由
"夹具确实生成 + 工具确实存在"双重守卫，基础设施故障一律记 skip）：

| 变异体 | 移植套件 | model_fuzz | iterator_snap | crash_torture | format_probe | bloom_oracle |
|---|---|---|---|---|---|---|
| hash_mult（bloom/缓存哈希乘法→加法） | caught | miss | miss | miss | miss（仅结构检查） | **caught**（官方 FilterPolicy 拒绝 kvdb 自己表里的 20/20 键——正是审计 F-1 假阴性类） |
| skip_wal（写路径跳过 WAL 追加） | caught | **caught** | miss | **caught**（P15 完整性断言修复后） | miss* | miss |
| batch_count（批计数不增） | caught | **caught** | **caught** | **caught** | miss* | miss |
| snap_leak（迭代器快照边界失效） | **missed** | miss | miss | miss | miss | miss |

\* 探针的 WAL 批计数检查只在 **WAL 仍存在**时可见；夹具做过压缩，WAL 已被
清理，故这两格记 miss——方法的边界而非缺陷（见 §8 TODO）。

结论（全部经复核后的诚实版）：
- **原套件放过 snap_leak 一类快照可见性变异**；补了反向扫描的迭代器快照腿
  仍没抓到它——因为该变异对正/反向全量扫描**近似等价**（旧版本被 DBIter 的
  同键合并吞掉）。等价变异是变异测试的固有局限，如实记账而非粉饰；
- **D 腿的"caught"曾经全是假阳性**（NULL 写选项 bug），修复后又发现其前缀
  性质允许"空前缀"从而放过"全丢 WAL"——**变异测试是发现检查器自身漏洞的
  唯一手段**（P14/P15）；
- bloom 成员性最终由**官方实现做 oracle** 承担（JS 自研版本四次在健康引擎上
  误报后退役）：hash_mult 被 oracle 精确捕获，20 键 0 假阴性（健康表）；
- 负向对照：D 腿在"故意丢一个已确认键"时如实报 rc=3，证明其非空转。

## 6. 对比验证：同种子双跑（实测）

同一 harness 分别链接官方归档与本仓归档：

| harness | 官方引擎 | kvdb | 结论 |
|---|---|---|---|
| model_fuzz 种子 1–3 × 1 万步 | 全绿 | 全绿 | 同一预言机下行为一致（二进制键、压缩、重开） |
| iterator_snapshot 种子 1–2 | 全绿 | 全绿 | 快照语义与参考实现一致 |
| crash_torture（300 次确认写 + 自毁 + 前缀校验） | 前缀成立 | 前缀成立 | 崩溃一致性语义一致 |
| format_probe --compare（20 键库，双方各写一份） | tables/wal/comparator **SAME** | — | 独立解析器眼里的内容摘要一致 |
| official_table_check（官方 reader，verify_checksums=true）读 kvdb 表 | — | 20/20 entries，status OK | 块级校验和下可读 |

判据说明：官方库在本机无 libsnappy 时把压缩降级为不压缩，因此"逐字节相同"
只在 no_compression 路径成立（doc/10 §4）；kvdb 自己的 snappy 块被 JS 解码
器验证**可解码**，输出字节等价性仍未证（§8 TODO）。
