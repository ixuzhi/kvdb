# 14 — 第三套验证体系：契约面审计（N1–N7）

本文是 2026-09-26 建立的**全新验证体系**的完整设计、实现与首轮结果。
建立动因：项目此前已有两代方法（doc/11 五层检查、doc/13 正交五腿），
本轮要求**忽略既有检查方式**、从零设计一套与它们正交的方法，回答两个问题：

1. **功能是否都实现了**——以官方公共 API 的完整清单为基准，而不是以
   "我们自己挑过的测试场景"为基准；
2. **接口与二进制是否和 leveldb 兼容、可互操作**——接口（源码级签名、
   链接级符号、ABI 替换）、二进制（落盘字节）、行为（同输入同输出）。

总入口：`bash tools/audit/audit_all.sh [quick|full]`。
证据留档：`build/audit/<时间戳>/`，退出码 = 失败腿数。

## 1. 与既有两代方法的正交性

doc/11 五层（L0 移植套件 / L1 黄金比对 / L2 跨后端 / L3 sanitizer /
L4 静态审计）的参照系是**官方断言**与**官方字节**；doc/13 五腿的参照系是
**自建预言机**（模型/解析器/物理事实）。两者回答的都是
"选定场景下对不对"——场景集合本身是第一代方法挑出来的，没有被系统性
追问过"**官方暴露面的每一项是否都被测到**"。

第三体系的切入点是**契约面**：官方 `c.h` 的每个函数签名、每个选项旋钮、
每个错误契约，逐一变成场景；官方导出符号表的每一项，逐一在 kvdb 归档里
点验；两引擎在同一确定性输入上的每一步输出，逐一比对。

| | doc/11 五层 | doc/13 五腿 | doc/14 六腿 |
|---|---|---|---|
| 场景来源 | 移植的官方测试 | 自建 harness 场景 | **官方 API/选项/符号清单逐项** |
| 判定参照 | 官方断言/字节 | 自建预言机 | **双引擎互相**（同输入→同输出） |
| 接口覆盖 | c_test 直连 16 phase | 只经公开面 | **签名级+符号级+ABI 替换常设** |
| 行为覆盖 | 断言级 | 物理事实级 | **逐步输出级**（同序列锁步） |
| 修复面覆盖 | recovery 用例 | 崩溃点已知 | **repair 交接 + 任意点 kill** |

## 2. 六腿结构

全部驱动（option_matrix / lockstep / corner_matrix / lifecycle / crash）
**只对官方 `leveldb/c.h` 编译一次、分别链两库**——这使每个驱动同时是
常设的 ABI 替换证明：kvdb 导出面缺任何符号，链接当场失败。

| 腿 | 驱动/脚本 | 判定 | 证明什么 / 不证明什么 |
|---|---|---|---|
| **N1 接口面机械审计** | `api_surface_audit.sh` | 签名清单归一化后集合相等；官方归档的每个 `leveldb_*` 符号在 kvdb 归档双向对齐；枚举常量一致；版本=1.23 | 接口兼容的**机械证据**；不证明行为 |
| **N2 选项×行为全矩阵** | `option_matrix.c` + `run_option_matrix.sh` | 官方 c.h 全部选项旋钮逐项成场景，同场景双引擎跑，must-equal 字段（扫描摘要/点查/快照读/错误类别/属性存在性）跨引擎相等；近似大小等实现定义字段只记录 | **"功能都实现了"的主证据**；不比文件字节 |
| **N3 同步锁步差分** | `lockstep.c` + `run_lockstep.sh` | 同种子随机序列（put/delete/get/批/扫/seek/快照/重开/压缩）分别跑两库，**每步 trace 逐行 diff**；进程内另有排序数组模型自检 | 同输入下两引擎**逐步**逻辑等价；不证明并发正确性 |
| **N4 格式角落矩阵** | `corner_matrix.c` + `run_corner_matrix.sh` | 20 个编码/布局角落场景（尺寸边界/二进制键/重启点/块尺寸/布隆位数/序列号增长/墓碑形态/WAL 分片边界/空库/空前缀族），strict 场景双引擎目录逐字节 diff（除 LOG*/LOCK），digest 场景 4 方向交叉读取摘要全等 | 格式兼容从"10 个固定负载"扩展到**参数化角落**；压缩路径不进字节比对（见 §5 环境门控） |
| **N5 交替生命周期+跨引擎修复** | `lifecycle.c` + `run_lifecycle.sh` | O→K→O→K→O 五程交替写/删/压缩 → 双引擎对模型 verify → 互做健康库 repair（幂等、双方可读）→ 破坏探针（删 WAL/截断表/改后缀）后修复分歧必须落在 EXPECTED 表内 | **跨引擎交接与修复的数据保全**；把 doc/10 M-2..M-6 的分歧从"代码审查结论"变成"可运行探针" |
| **N6 随机崩溃+跨引擎恢复** | `crash.c` + `run_crash.sh` | 随机时刻 kill -9 写入进程 → 前缀性质（已确认写全在场且值正确）+ **两引擎恢复出的键集摘要必须全等**；确定性 WAL 尾截断轮：同开或同拒 | 任意崩溃点的恢复语义跨引擎等价；不证明机器断电（fsync 级）一致性 |

横切纪律（沿用 doc/11 三原则，新增两条）：

4. **预期分歧必须登记**——已知合法差异（实现定义的行为、已归档缺陷的
   探针）写进各腿的 EXPECTED 表；出现在表内记 EXPECTED/CAUGHT，
   表外分歧才是 FAIL。这使"检出已知缺陷"从事故变成制度（N7）。
5. **装置缺陷照记不误**——首轮即遇到 6 处（§6），与引擎发现同等入档。

## 3. N7 方法自证：以已归档缺陷为标本的检出力矩阵

不用人工变异体（doc/13 的做法），而是把**doc/10 已归档且确认未修**的缺陷
作为天然标本：新体系跑完后，每个标本必须被某条腿恰好捕获。

| 标本（doc/10 编号） | 内容 | 预期捕获腿 | 首轮实测 |
|---|---|---|---|
| M-1 | paranoid 下 <12B WAL 记录被静默跳过，Open 仍成功（官方 reporter 使 Open 失败） | N2 `paranoid-small-record` 场景 errclass 分歧 | **CAUGHT**（官方 errclass=1，kvdb=0） |
| F-2 | WriteBatch `count==0` 提前返回 OK，不校验残留负载（官方 found!=Count 判 corruption） | N2 `paranoid-count0-wal` 场景（驱动手工伪造 CRC 正确的 count=0+负载记录） | **CAUGHT**（官方 errclass=1，kvdb=0） |
| M-4 | repair 坏 key 即删整表（官方保留可解析前缀） | N5 截断最大表后修复 | CAUGHT（两侧都 DATALOSS，形状见 N5 输出） |
| M-5 | repair 只认 .ldb 不认 .sst（官方回退） | N5 改后缀探针 | **CAUGHT**（kvdb 丢数据，官方保全） |
| F-1 / C-1 / F-3 / F-4 | filter 假阴性 / 跳表内存序 / CRC 表竞争 / NewId 竞争 | 本机（Windows，TSan 不可用；竞争需并发首调）**不在检出范围**，登记为环境门控缺口 | NOT-COVERED（§7） |

结论：**N2/N5 对"行为分歧类"缺陷的检出力得到实证**；并发/内存序类
标本明确声明不在本体系覆盖内（那是 L3/TSan 的地盘，Windows 无 TSan）。

## 5. 环境门控与已知边界

- **官方参考库无 libsnappy**（msys 构建）：写请求 snappy 时官方静默降级为
  不压缩，读压缩块报 corruption。因此本体系所有跨引擎字节/恢复比对统一
  `no_compression`（与 run_golden/run_interop 同一纪律）；压缩路径的行为
  等价由 N2 的 compression 场景单独覆盖（只比内容摘要，不比字节）。
  snappy 压缩块的互操作问题已在 doc/08 §7 用 HAVE_SNAPPY=1 的 Linux 构建
  闭环过（块级互操作成立、压缩器不位相同），本体系不重复。
- **TSan/LSan 在 Windows 不可用**（doc/09 §4.3）：C-1/F-3/F-4 类并发标本
  与泄漏维度不在本机检出范围。原生 Linux 上把本体系六腿接入
  `run_sanitizers.sh` 即可补全。
- **approximate_sizes 是实现定义**：两引擎数字不同（P2-7 压缩调度差异的
  直接观测），N2 把 size 字段列为 RECORD（记录不比对）。
- **destroy-open 场景是平台敏感的**：msys 的 POSIX 层上"删除别人打开的
  文件"行为介于真 POSIX 与 Win32 之间，该场景的两引擎分歧读数要结合
  平台解读（见首轮读数）。

## 6.1 本体系发现的新引擎级分歧（未修，登记进 doc/06）

### D-1：`env_posix` 的 LOCK 缺少官方的进程内持锁集合（由 N2 destroy-open 场景逼出）

- **现象**：N2 `destroy-open` 场景跨引擎 errclass 分歧（kvdb=0 成功 / 官方=1 报错）。
- **定位**：官方 `DestroyDB` 先 `LockFile`，被占用报 `IO error: lock …/LOCK: already held by process`；kvdb 的 `ldb_destroy_db`（db.c）同样取锁，却取成功了。继续用同进程双 `leveldb_open` 探针复现：官方报同一错误，kvdb 允许第二个实例打开同一目录。
- **根因**：两边 env_posix 都用 `fcntl(F_SETLK)`——但 fcntl 锁是**进程级**的，同进程第二次加锁必然成功。官方 `env_posix.cc:494` 为此显式维护了一个互斥保护的进程内持锁集合（注释原话："fcntl(F_SETLK) does not provide any protection against multiple uses from the same process"）；kvdb 的 `env_posix.c`（env_posix.c:271 一带）没有这个集合。`env_win` 有进程内计数（doc/09 W5 之前记录的那一半），所以该分歧**只在 POSIX 后端（msys/Cygwin/Linux）成立**。
- **后果**：① 同进程对同一目录开两个 DB 实例在 kvdb/POSIX 上不会被打拒——两个实例并发写同一目录是数据损坏形状；② `destroy_db` 在打开状态下"成功"删除目录（官方拒绝并保留目录），打开中的实例变成对着已删除文件继续跑。
- **修复建议**：env_posix 的 `lock_file` 加一把互斥锁保护的已持有锁表（对齐官方），含负向对照用例（同进程双开必须报错、destroy-while-open 必须报错）。已固化为 N2 的 `lock-same-process` 场景（`double_open_errclass` / `destroy_open_errclass` 两个字段），在分歧修复前挂在 EXPECTED 表里作为活体标本。

### D-2（观察，非缺陷）：同等 write_buffer 下 kvdb 的 flush 粒度约为官方一半

N4 `multibuf` 场景（write_buffer=64KiB，1600 条 ×~90B）：官方 3 张 ~48KB 表，kvdb 6 张 ~24KB 表——两引擎最终摘要一致、数据无损，但 memtable 使用量记账口径不同导致 flush 边界不同。这是 P2-7"压缩调度差异"的又一观测面，只影响文件数量/大小分布，不影响正确性。登记不修。

## 8. 一句话结论

> 在"官方 API 逐项、同输入逐步、文件逐字节、崩溃任意点"四个新维度上，
> kvdb 与官方 leveldb 的 C 接口（69 签名/68 符号/枚举/版本）、行为
> （10 万+ 锁步操作、32 个选项场景、14 次随机崩溃恢复）、磁盘格式
> （19 个角落场景逐字节）**全部对齐**；本体系同时以黑盒方式确认了
> 一条此前未知的引擎级分歧 **D-1**（env_posix 缺进程内持锁集合），
> 并实证捕获了三件已知未修缺陷（M-1、F-2、M-5）——新方法的检出力
> 由此成立。修复 D-1 与 M-1/F-2 后，本体系六腿应全绿（EXPECTED 表
> 清空），这是下一步的明确验收标准。
